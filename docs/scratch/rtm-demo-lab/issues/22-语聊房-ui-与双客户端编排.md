## Answer

**分层**：把「时序」和「渲染」彻底分开——顺序敏感的编排全在不依赖 React 的 `orchestrator.ts` 里，组件只发意图。

| 文件 | 职责 |
| --- | --- |
| `orchestrator.ts` | 双客户端编排器：连接顺序、代数守卫、麦位激活时序、失败回滚。框架无关（`getView()` + `subscribe()`） |
| `VoiceRoomScene.tsx` | 只管 React 生命周期与视图订阅、身份推导、trace 来源上交 |
| `components/actions.ts` | `PhoneActions`——组件能调的动作面，全部返回 `void` |
| `components/*.tsx` | 七个区块 + `PhoneFrame` + 两条常驻告警，纯展示 |
| `testing.ts` | 语聊房测试替身，供外壳测试与场景测试共用 |
| `app/sceneContext.ts` | 跨路由边界传 `env`、trace 回调、测试注入口 |

编排器**刻意不依赖 React**：连接顺序、生命周期守卫、媒体驱动的激活时序都能脱离 `useEffect` 的调度细节测试。组件拿不到客户端也拿不到 RTC，所以改不坏时序。

**逐条对照**

- **先连房主再连听众** —— `start()` 里 `host.connect()` → `hostRtc.join()` → `audience.connect()` → `audienceRtc.join()`，每步之后比对代数。房间快照由房主创建（听众端刻意不写初始快照），听众先连会读到空 Storage 白等一轮。测试：`先连房主再连听众 —— 房间快照由房主创建，听众先连会白等一轮`、`听众的 RTC 只加入频道，不发布麦克风 —— 上麦成功才发布`、`房主连接失败时不继续连听众，并把错误留在房主端视图上`。
- **StrictMode 不泄漏** —— **两层守卫，缺一不可**。React 侧每次挂载建一个新编排器实例；编排器内部再有 `generation` 计数器，`start()`/`stop()` 都递增，每个 `await` 之后比对。只有计数器的话第二代会复用第一代已 `stop()` 的客户端；只重建实例的话第一代的 `connect()` 仍会在后台跑完并留下连接。测试：`start() 期间被 stop()，后续步骤全部放弃 —— 不会连上听众`、`第二代 start() 正常完成，不受第一代影响`、`StrictMode 下重复挂载卸载不泄漏连接：断开次数不少于连接次数`、`StrictMode 下渲染出的手机不重复 —— 每台只有一个`。
- **卸载断开两端** —— `stop()` 递增代数后 `Promise.all` 四个 `swallow()` 过的拆除（两个 RTC leave + 两端 disconnect）。测试：`卸载时两端都断开`、`stop() 关闭两端与两个 RTC`。
- **耳机告警** —— 文案与遗留实现逐字一致。测试：`渲染耳机告警 —— 两端都会真实播放音频`、`两条告警都常驻页面，不是可折叠的小字`。
- **生产边界告警** —— 标题就是「踢出、封禁、强制麦控都是客户端协作行为，不构成信任边界」。有一条专门的负向断言守着措辞：`生产边界告警不含「已强制执行」这类表述`。
- **麦位激活由媒体结果驱动** —— 房主 `approveSeatRequest` 只把麦位置 `joining`；听众收到 `seat.approved` 后先 `publishMicrophone()`，**成功才** `activateOwnSeat()`；抛错则 `rollbackOwnSeat()` 且不激活，同时在听众端视图留下「上麦失败：…」。六条测试锁住：`房主同意申请只置 joining，不直接激活`、`收到 seat.approved 后：先发布麦克风，成功才激活麦位`、`发布麦克风失败：回滚麦位，且不激活`、`失败路径给出可见反馈 —— 听众端视图上留下错误文案`、`接受邀请同样走「发布成功才激活」`、`seat.invited 只是通知，不擅自发布麦克风`。**不要为了少一次 Storage 写把它改成先激活后发布**——那样会在房间里留下一个不发声的「已上麦」用户。
- **迁移遗留 UI** —— 遗留的 508 行拆成七个区块组件塞进手机外框。唯一没搬的是 `EventTimeline`，它被票 20 的共享面板取代（遗留文件本身按项目约束原地保留，未删）。
- **布局数值** —— jsdom 不做布局，`getComputedStyle` 拿不到这些值，所以新增 `app/styles.test.ts` 直接断言样式表文本：`height: min(812px, calc(100vh - 210px))`、麦位 `min-height: 76px`、头像 `26px`、`repeat(4, minmax(0, 1fr))`、断点 `1240px`。**最关键的一条是 `公屏是唯一纵向滚动的区块`**：用正则把语聊房段落里所有 `overflow-y: auto|scroll` 的规则全捞出来，断言恰好只有 `.vr-chat`。这条当场抓到一个违规——角色面板的申请列表自带 `max-height: 96px` + `overflow-y: auto`，已删除（`MAX_CLIENTS = 2`，最多一条待审申请，那个滚动条本就是死代码）。
- **区块顺序** —— 断言 `.vr-phone` 的直接子节点类名序列恰好是状态栏、房间头部、麦位网格、角色面板、成员条、公屏、操作条。测试：`自上而下：…`、`听众端区块顺序与房主端一致 —— 只有区块内容不同`、`底部操作条是公屏的兄弟节点且排在最后 —— 常驻手机框内，不随公屏滚走`。
- **身份条 badge 同色** —— 颜色走票 20 的 `roleColor(role)`，与时间线**同一个函数**，两处不可能漂移。测试：`badge 颜色取自 roleColor —— 与时间线里的 badge 同源同色`、`两端 badge 颜色不同 —— 读者靠颜色而不是文字判断来自哪一端`。

**三个设计上的取舍**

**结构接口而不是类。** `VoiceRoomClients` 引用手写的 `VoiceRoomHostClientLike` / `VoiceRoomAudienceClientLike`，不是具体类。类里有 `private` 成员，TS 的结构化匹配会因此判定任何对象字面量都不兼容——测试就只能去 `new` 真客户端或者强转，两条路都会把「注入假工厂」这个口子堵死，而那正是本票明确要求的。

**`getView()` 不能再拷一层。** `patch()` 每次整体换新对象、绝不原地改，所以 `this.view` 本身就满足 `useSyncExternalStore` 的硬要求：没变化时返回同一引用。我一开始加的记忆化不只是多余，**按引用拷会正好破坏这个性质**导致无限重渲染。已删除并留注释警告不要加回来。

**测试替身单独一份。** `orchestrator.test.ts` 里那份假客户端记录 `operations: string[]` 用于断言跨端调用顺序；`testing.ts` 那份只求「不发网络请求、能被驱动」。刻意不合并——合并出来的东西会同时被两批测试的需求拉扯。

**接进外壳**：`LabShell` 现在持有 trace 来源状态，用 `useCallback` 稳定的 `publishTraceSources` 交给场景（必须稳定引用，场景把它放进 effect 依赖），空数组统一收敛到模块常量 `NO_TRACE_SOURCES`。票 20 留的 `sources={NO_TRACE_SOURCES}` 占位已换成真实来源。`LabRoutes` 多一个 `voiceRoomOverrides` 注入口，**只有测试传**——场景一挂载就自动连接，外壳测试不注入替身就会去连真实 RTM。

**一个坑**：`styles.test.ts` 起初用 `node:fs` 读样式表，Vitest 跑得过但 `tsc -b` 报三个 TS2591——`tsconfig.app.json` 的 `types` 刻意不含 `node`（app 是浏览器包，不该看见 `process`/`Buffer`）。项目里已有现成约定，改用 Vite 的 `styles.css?raw`。**这就是为什么汇报构建状态必须跑 `npm run build` 而不是只跑测试。**

**验证**：`npx vitest run src/scenes/voice-room/VoiceRoomScene.test.tsx` 21 passed；`npx vitest run src/app/styles.test.ts` 9 passed；`npm test` 全量 404 passed / 27 files（根）+ 64 passed / 11 files（demos）；`npm run build`（含 `tsc -b`）绿。
