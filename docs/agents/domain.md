# 领域文档约定

说明工程类技能在探索本仓库时，应该如何消费领域文档。

## 动手之前先读这些

- 根目录的 **`CONTEXT.md`** —— 项目术语表。
- **`docs/adr/`** —— 与本次改动相关的架构决策记录（ADR）。

如果这些文件还不存在，**静默跳过即可**。不要提示它们缺失，也不要建议提前创建。它们由 `/domain-modeling` 技能（通常经 `/grill-with-docs` 或 `/improve-codebase-architecture` 触发）在术语或决策真正需要落定时惰性创建。

## 布局：单上下文

本仓库只有一个应用，即根目录 `src/` 下的 RTM 场景实验室，因此采用**单上下文**布局，只需要一份术语表。已经归档的历史实现属于相邻的 `new-rtm-demo-legacy` 仓库，不参与本仓库的领域文档布局。

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-<slug>.md
│   └── 0002-<slug>.md
└── src/
```

ADR 命名为 `NNNN-<slug>.md`，四位序号从 `0001` 起递增。

若将来仓库拆成多个互不相通的领域，才需要改成多上下文布局（根目录 `CONTEXT-MAP.md` 指向各上下文自己的 `CONTEXT.md`）。目前不需要。

## 使用术语表里的词

当输出中出现领域概念时——issue 标题、重构提案、假设、测试名——一律使用 `CONTEXT.md` 中定义的写法，不要漂移到术语表明确回避的同义词。

如果需要的概念还不在术语表里，这本身就是个信号：要么是在发明项目并不使用的语言（该重新考虑），要么是真的存在空缺（记下来交给 `/domain-modeling`）。

本项目已有一批含义明确、不应随意替换的术语，例如：麦位（seat）、排麦（seat request）、快照（snapshot）、权威状态（authoritative state）、治理命令（governance command）、场景（scenario）、一级分类与二级场景。这些词在写入 `CONTEXT.md` 之前，先沿用代码和现有文档里的既有用法。

## 与 ADR 冲突时要显式指出

如果输出与既有 ADR 相矛盾，不要默默覆盖，要明确摆出来：

> _与 ADR-0007（事件溯源订单）冲突——但值得重新讨论，因为……_
