## 1. 多实例支持与上限

### 1.1 官方立场：明确不推荐，且明确写了「不支持多实例同时登录」— confirmed

SDK 自带的类型定义在 `RTMClient` 构造函数上直接写了这件事。原文（`agora-rtm.d.ts:2174` 与 `:2181`）：

> - 推荐全局只创建一个 RTM 实例，生命周期同你的 APP，不推荐在 Vue mounted，data 等组件钩子函数中创建 rtm。RTM 不支持多实例同时登录，请避免引发多实例互踢问题。

> - It is recommended to create only one RTM instance globally, with the same lifecycle as your APP, it is not recommended to create rtm in Vue `mounted`, `data`, etc. RTM does not support simultaneous login from multiple instances, please avoid multi-instance mutual kick issues.

本地知识库口径一致，`content/releases/web-rtm-2.3.0.md:62`：

> - 推荐每个应用生命周期使用一个全局 RTM 实例；多框架、多 WebView 或 Electron 场景需避免重复初始化。

`content/resources/web-rtm-multi-instance-identification.md:46` 也把实例生命周期绑定到 app 生命周期：

> 5. SDK 实例生命周期应与 app 生命周期绑定，事件监听器也应由同一生命周期统一安装和移除。

**重要的措辞辨析**：`.d.ts` 的「不支持多实例同时登录」与 `2.3.0` 新增的 `DUPLICATE_USER_ID` 错误放在一起看，指向的是**同一 userId 的多实例互踢**，而不是「同一页面禁止存在多个不同 userId 的实例」。理由见下一节：SDK 的实例注册表是按 `appId-userId` 组合去重的，如果目标是禁止任何多实例，就不需要把 userId 纳入 key。这条辨析属于 **probable**（是对两处一手证据的合并推断，官方没有一句话直说「不同 userId 的多实例是被支持的」）。

### 1.2 硬约束：同一 `appId + userId` 的第二个实例会在构造期直接抛错 — confirmed

`2.3.0` 的新增错误，知识库 `content/releases/web-rtm-2.3.0.md:40`：

> - 同一项目和用户组合已被活跃实例占用时，新增 `DUPLICATE_USER_ID` 错误。

实现位于 bundle 偏移 `434726`（`cf` 是模块级 `Set`）与 `434992`（构造函数入口的检查）：


实测：同 `appId` 下 12 个不同 userId 全部构造成功；重复 `appId+userId` 抛 `code=-10027`。

### 1.3 ⚠️ 这个注册表只 `add` 不 `delete`：`logout()` 之后同一 userId 无法重建 — confirmed

全 bundle 中 `cf` 只出现 3 次：声明（`434726`）、`cf.has`（`434992`）、`cf.add`（`438699`）。**没有任何 `cf.delete`**。`cf.add` 位于构造函数末尾：

```js

```

实测确认了后果：`logout()` 正常 resolve 之后，用同一 `appId+userId` 再 `new AgoraRTM.RTM(...)` **仍然抛 `-10027`**。也就是说这个"占用"标记在页面生命周期内**永不释放**，`Set` 的语义是「这个 uid 在本 JS 运行时用过」，不是「当前有活跃实例」。文案里的 `another active RTM instance` 与实现不符。

这一条对本项目有直接影响，见第 5 节。

### 1.4 逃生开关 `IGNORE_DUPLICATE_USER_ID_ERR` 存在，但不应作为产品方案 — confirmed

默认值 `false`（偏移 `127569`），置 `true` 可完全跳过上述检查（实测：不再抛错）。知识库 `content/resources/web-rtm-private-parameter-version-matrix.md:70` 给了定位：

> | `IGNORE_DUPLICATE_USER_ID_ERR` | 2.3.0 | 多实例兼容控制；常规多实例验证与重复实例报错专项需要使用不同设置 |

同文件 `:77` 对这一类参数的边界：

> 以下参数按用途评审，不应作为客户业务代码的长期依赖：

它是 `setParameter` 的**进程级全局**开关（见 2.2），不是 per-instance 选项。

### 1.5 实例数量上限：**官方文档与知识库均未说明具体数字** — inconclusive

这一点必须明确留空，不填数字：

- 全 bundle 检索 `MAX_INSTANCE`、`instanceCount`、`INSTANCE_COUNT` 均为 **0 命中**；`RTM_ERROR_*` 中与 `EXCEED_LIMITATION` 相关的 8 个错误码全部是频道 / Topic / metadata / 速率维度，**没有任何「实例数超限」错误码**。
- 知识库、`.d.ts`、README 均未给出实例数上限。
- 实测在 jsdom 中构造 64 个实例无异常（但这只证明**构造期**无硬编码上限，不证明 64 个实例登录后可用；登录、Presence、服务端并发与计费行为未验证）。

**结论：SDK 侧不存在硬编码的实例数上限，超限没有专用错误码；真实上限由 WebSocket 数、内存/CPU、以及服务端并发与计费策略决定，需要实测。任何具体数字都不应写进设计文档。**

### 1.6 确实存在的、有明确数字的上限是「每实例频道数」— confirmed

参数定义（偏移 `121065`）：

```js
STREAM_CHANNEL_COUNT:{type:"number",defaultValue:10,max:100},MESSAGE_CHANNEL_COUNT:{type:"number",defaultValue:50}
```

超限抛 `RTM_ERROR_CHANNEL_INSTANCE_EXCEED_LIMITATION`，Message 侧校验在偏移 `1374422`，Stream 侧在 `1198975`：

```js
const A=Ph("STREAM_CHANNEL_COUNT");if(this._getStreamChannelList().length>=A){this.log("exceed join channel limit ".concat(A));
```

即：**每实例** Message Channel 默认 50 个、Stream Channel 默认 10 个（上限 100）。这是 per-instance 而非 per-page 的配额，多实例场景下不是瓶颈。

### 1.7 `Ins#` 编号来自一个**跨库共享的全局计数器** — confirmed

日志前缀 `Ins#<id>`（知识库 `content/stable/web-log-observability.md:32`、`content/resources/web-rtm-multi-instance-identification.md:38` 都用它做多实例辨识）的来源是挂在 `globalThis` 上的计数器（偏移 `154970`）：

```js

```

`w` 即 `globalThis`（偏移 `13297`：`w="undefined"!=typeof globalThis?globalThis:...`）。

实测：宿主页面先设 `globalThis.__global_unique_id__ = 500`，则第一个 RTM 实例的 `Ins#` 是 **501**。这意味着 `Ins#` 编号不是 RTM 私有的，任何使用同名 `__global_unique_id__` 约定的库（这是 `global-unique-id` 类小工具的通用 key）都会推高它。

排障影响：`Ins#` 编号**不能**用来推断「本页创建了几个 RTM 实例」，只能用来区分实例。知识库 `web-rtm-multi-instance-identification.md:38` 的判据「任一相关日志出现 `Ins#<id>` 且编号大于首实例」在被嵌入的页面里可靠性下降 —— 编号可能从一个非 1 的基数开始。这是对知识库既有判据的一个**补充边界**（probable，基于实现与实测，知识库未记录此情形）。

另外注意构造期这条 `logError`（偏移 `438622`）：只要 `Ins#>1` 就会**以 error 级别**打印 `please pay attention to avoid mutual kick issues or client mix-up issues`。多实例 demo 会稳定产生这条 error 日志，属预期噪声，不是故障信号。

## 2. 事件监听器隔离

### 2.1 回调严格隔离，不会串台 — confirmed（含实测）

结构上，公开 `RTMClient` 继承 `EventBase` → `EventEmitter`（`agora-rtm.d.ts:303`、`:2169`）：

```ts
declare class EventBase<T = Record<string, never>> extends EventEmitter {
declare class RTMClient extends EventBase<RTMEvents.RTMClientEventMap> {
```

而 `addEventListener` 转发给该实例私有的 `_rtmImpl`（偏移 `439303`），`_rtmImpl` 再存进自己的 EventEmitter（偏移 `1377672`）：

```js
addEventListener(A,e){this._rtmImpl.addEventListener(A,e)}removeEventListener(A,e){this._rtmImpl.removeEventListener(A,e)}
addEventListener(A,e){this.on(A,e)}removeEventListener(A,e){this.off(A,e)}
```

实测（两个实例 c1/c2，各注册一个 `message` 监听）：

- `_rtmImpl` 对象各自独立，`_events` 不共享
- 在 impl1 上 emit → 只有 h1 触发（h1=1, h2=0）；在 impl2 上 emit 两次 → h1 仍为 1，h2=2
- 在 c1 上 `removeEventListener` 不影响 c2
- `presence` / `storage` / `lock` 模块包装器各实例独立

`message`、`presence`、`storage`、`lock`、`topic`、`linkState`、`token`、`tokenPrivilegeWillExpire` 都在同一个 `RTMClientEventMap`（`agora-rtm.d.ts:1597`）里走同一条 EventEmitter 通路，因此**上述隔离性对所有事件类型一致成立**。

补充：原生 `addListener` / `removeListener` 被**故意禁用**（偏移 `178358` 的 `banOriginEventListener` 分支，实测 `addListener`/`removeListener` 均为 `undefined` 且不可写）：

```js
g&&(u=this,Object.defineProperty(u,"addListener",{value:void 0,writable:!1,configurable:!1}),Object.defineProperty(u,"removeListener",{value:void 0,writable:!1,configurable:!1}))
```

所以只能用 `addEventListener` / `removeEventListener`。

### 2.2 关于 `.d.ts` 里「所有事件为全局事件」的辨析 — probable

`agora-rtm.d.ts:2175` / `:2371` 的原文：

> - RTM 所有事件为全局事件，建议创建实例后立即监听，否则可能错过一些事件，非必要无需多次监听。

> @remarks All events of RTM are global events, it is recommended to listen to them immediately after creating the instance, otherwise you may miss some events, it is not necessary to listen multiple times.

结合 2.1 的实测，这里的 "global" 应理解为**在单个实例内跨所有频道全局**（不需要 per-channel 注册），而不是「跨实例共享」。标 probable 是因为这是对措辞的解读，官方未澄清；但实测已经排除了「跨实例共享」这一读法。

### 2.3 确实存在的共享全局状态（这是本节的关键风险）— confirmed

事件回调本身隔离，但以下状态是**跨实例共享**的：

| 共享状态 | 位置（偏移） | 影响 |
| --- | --- | --- |
| `setParameter` / `getParameter` 配置单例 `Hh` | `128028`，导出见 `agora-rtm.d.ts:2440` | **进程级**。任一处 `AgoraRTM.setParameter(k,v)` 影响页面内全部实例，无法 per-instance 覆盖。实测：设一次后所有实例 `getParameter` 同值 |
| `setArea` 区域配置 | `agora-rtm.d.ts:2433`（`Hh.setAreaConfig`） | 同上，全局单一区域设置 |
| 重复 uid 注册表 `cf` | `434726` | 模块级 `Set`，只增不删（见 1.3） |
| `__global_unique_id__` 实例编号 | `154970` | 挂在 `globalThis`，跨库共享（见 1.7） |
| `window` online/offline 监听 | `119458` | 一组共享回调 `ch`，首个实例装、最后一个实例卸，引用计数正确 |
| 远程配置 localStorage 缓存 | `337868` | key `_agora_rtm_custom_config`，按 `appId` 分桶；同 appId 的多实例共享同一份缓存 |
| 全局 `AgoraRTC` 参数 | `1197263` | 创建 StreamChannel 时 RTM 会改写全局 RTC 参数，见第 4 节 |

**没有**共享的是：连接池（每实例自己的 `Connection` / 双 socket）、日志上传器（`Nd.instances` 按 `processId` 分桶，每实例一个 `processId`，偏移 `167576`）、`Context`（知识库 `content/stable/rtm-web-sdk-architecture.md:42` 明确 `Context` 是「实例生命周期内的共享状态容器」）。

**实践结论**：多实例之间不会串事件，但**任何配置类调用都是全局的**。不要试图给不同实例设不同的 `setParameter` / `setArea`；`logLevel` 等构造参数才是 per-instance 的。

## 3. 嵌入约束（作为页面被挂进上层网站）

### 3.1 存储依赖：只用 localStorage，不用 IndexedDB / sessionStorage / cookie — confirmed

全 bundle 计数：`localStorage` 8 处，`indexedDB` **0**，`sessionStorage` **0**，`document.cookie` **0**。

实际用途只有两类：

1. **远程配置缓存**（偏移 `337868`、`339076`）。key 由 SDK 类型决定：

```js
_getStorageKey(){return"miniapp_rtm"===this._sdkType?"_agora_rtm_miniapp_custom_config":"_agora_rtm_custom_config"}
```

存取实现（偏移 `336611`）：

```js
{getItem(A){return"undefined"==typeof localStorage?null:localStorage.getItem(A)},setItem(A,e){"undefined"!=typeof localStorage&&localStorage.setItem(A,e)},...}
```

2. 第三方 `debug` 库的 `debug` / `DEBUG` key（偏移 `161298`），且**已包在 try/catch 里**。

### 3.2 ⚠️ 严重：`sandbox` iframe（无 `allow-same-origin`）下 `login()` 会直接失败 — confirmed（实测）

注意 3.1 中那段存取代码：它只判断 `typeof localStorage === "undefined"`，**没有 try/catch**。而规范要求在不透明源（opaque origin）下访问 `localStorage` 是**抛异常**，不是返回 undefined。

HTML 规范（<https://html.spec.whatwg.org/multipage/browsers.html>）关于 sandbox 的原文：

> The sandboxed origin browsing context flag
> This flag forces content into an opaque origin, thus preventing it from accessing other content from the same origin. This flag also prevents script from reading from or writing to the `document.cookie` IDL attribute, and blocks access to `localStorage`.

该 flag 在 `sandbox` 属性不含 `allow-same-origin` 时设置。取值时抛 `SecurityError`（HTML 规范 web storage 一节）。

调用链：`login()` → `_genLoginImpl('first')`（偏移 `1407952`）→ `this._context.customConfig.init(sid)` → `_getStorageConfig()` → `localStorage.getItem`：

```js
case"first":null===(e=this._context.customConfig)||void 0===e||e.init(this._context.sid),await this._loginImpl({...});
```

`init` 内部（偏移 `337868`）`const e=this._getStorageConfig();` 也没有 try/catch。

实测（jsdom + 会抛 `SecurityError` 的 `localStorage`）：

- 构造 `new AgoraRTM.RTM(...)`：**不抛**（构造期不碰 localStorage，64 个实例均正常）
- `_storageRuntime.getItem` / `setItem`：**抛 `SecurityError`，SDK 内部无 try/catch**
- `login({token})`：**reject，`name=SecurityError`、`code=18`、`msg=The operation is insecure.`**

也就是说错误会以一个**非 RTM 错误码的原生 DOMException** 形式从 `login()` 冒出来，业务侧的 `mapRtmError` 之类映射会认不出它。

对照：`agora-rtc-sdk-ng` 4.24.6 把**每一处** `localStorage` 访问都包了 try/catch（如偏移 `264545` 的 `YP()`、`332084` 的 `tk()`/`nk()`），因此 RTC 侧在同样环境下只降级不报错。**这是 RTM 与 RTC 的一处实现差异，短板在 RTM。**

规避方式（按优先级）：
- iframe 的 `sandbox` **必须包含 `allow-same-origin`**（同时需要 `allow-scripts`，否则脚本根本不执行）；
- 或者上层不加 `sandbox`；
- 或者在加载 SDK 前注入一个「吞异常」的 `localStorage` shim（可行但属 hack，会一并影响 RTC）。

补充边界：`customConfig` 只在**非私有化部署**时创建（偏移 `428896`：`if(this.rtmConfig.privateConfig){...}else this.customConfig=new PR(this.appId)`）。即私有化部署配置下不会走这条 localStorage 路径。本项目走公网 prod，属于会命中的那一侧。

### 3.3 跨域 iframe（未 sandbox）：storage 被分区但不被阻断 — confirmed

Chrome 的存储分区（Chrome 115 起对所有用户默认开启）原文（<https://github.com/GoogleChrome/developer.chrome.com/blob/main/site/en/docs/privacy-sandbox/storage-partitioning/index.md>）：

> Partitioning generally means that data stored by storage APIs like local storage and IndexedDB by an iframe will no longer be accessible to all contexts in the same origin. Instead, the data will only be available to contexts with the same origin and same top-level site.

对 RTM 的实际影响很小：`_agora_rtm_custom_config` 只是远程配置的**缓存**，分区后无非是每个 top-level site 各存一份、首次进入时缓存未命中。缓存未命中不阻断登录（`_query()` 会走网络拉取，偏移 `339076`）。

**结论：跨域 iframe 本身不构成 RTM 阻断项；真正的阻断项是 `sandbox` 缺 `allow-same-origin`（见 3.2）。**

### 3.4 `sandbox` 不阻断 WebSocket 本身 — confirmed

WebSockets 规范全文检索 `sandbox` / `opaque` / `SecurityError` 均为 0 命中；HTML 规范的 sandboxing flag 清单里也没有任何一项涉及 socket / network。所以不透明源的 iframe 可以正常 `new WebSocket(...)`（前提是有 `allow-scripts`）。

两点附带注意：
- 握手会带 `Origin: null`（推导自 HTML 规范「不透明源序列化为 `null`」，非 WebSocket 规范直述）—— **probable**，若服务端做 Origin 校验需实测。
- CSP `connect-src` 会管住 WebSocket。CSP Level 3 §6.1.2 原文：

> This directive also controls WebSocket [WEBSOCKETS] connections, though those aren't technically part of Fetch.

且在不透明源下用 `connect-src 'self'` 很可能匹配不到任何 `wss://host`，应显式列出主机名而不要依赖 `'self'`（**probable**，规范未对该情形给出无歧义结论）。

### 3.5 域名白名单与端口 — confirmed（清单来自 bundle，非官方公开文档）

从 bundle 中提取到 **100** 个硬编码域名，分为四类：

- AP 接入：`ap-web-1.agora.io`、`ap-web-2.agora.io`、`ap-web-{1,2}-<region>.agora.io`、`web-{1,2,3,4}.ap.sd-rtn.com`、`webrtc2-{2,4}.ap.sd-rtn.com`
- Cloud Proxy：`webrtc-cloud-proxy.sd-rtn.com`、`<region>.webrtc-cloud-proxy.sd-rtn.com`、`proxy-ap-web-<region>.agora.io`、`proxy-ap-web.agoraio.cn`
- 日志上传：`logservice-rtm.agora.io`、`rtm.logservice.sd-rtn.com`、`logservice-<region>.agora.io`
- 事件上报：`rtm.statscollector.sd-rtn.com`、`statscollector-{1,2}-<region>.agora.io`、`webcollector-rtm.agora.io`

默认 edge WebSocket 端口（偏移 `120494`）：

```js
const Uh={0:9591,1:9593},Fh={0:9590,1:9592};
```

`Uh` 为 Web（env0=9591 / env1=9593），`Fh` 为 miniapp。与知识库 `content/stable/environment-evidence-matrix.md:42` 一致：

> - 已有 edge 但没有 WebSocket connect：检查目标、端口与网络；常见端口包括 `9591`、`9593`，部分 `2.1.x` 环境还涉及 `27387`。

Cloud Proxy 场景回落 443（登录 `finally` 中的 `port fallback to 443` 日志，偏移 `1366521` 附近）。

注意 `2.3.0` 改了 Cloud Proxy 默认值，知识库 `content/releases/web-rtm-2.3.0.md:49`：

> - auto fallback Cloud Proxy 默认关闭；需要代理时应显式打开 Cloud Proxy，并单独决定是否允许自动 fallback。

**未说明项**：上述清单是从 bundle 反推的，**官方文档中面向客户的「防火墙/白名单」正式清单本次未取到**，不应把这 100 个域名当作官方承诺的完整集合（区域、私有化部署、后续版本都可能不同）。生产环境的白名单应向 Agora 侧确认。

### 3.6 RTC 在跨域 iframe 需要显式授权 — confirmed

如果嵌入场景还要开麦克风/摄像头，跨域 iframe 必须显式委派权限。mediacapture-main 规范原文：

> This specification defines two [=policy-controlled features=] identified by the strings "camera" and "microphone". Both have a [=policy-controlled feature/default allowlist=] of "self".

`'self'` 意味着**默认不委派给跨域子框架**。上层需要写：

```html
<iframe src="https://demo.example/..." allow="camera; microphone" sandbox="allow-scripts allow-same-origin"></iframe>
```

（`allow-same-origin` 是 RTM 的要求，见 3.2；`allow="camera; microphone"` 是 RTC 的要求。）

## 4. RTM + RTC 共存

### 4.1 版本耦合 — confirmed

`package.json`：

```json
"peerDependencies": { "agora-rtc-sdk-ng": "^4.24.3" }
```

RTM bundle 把 `AgoraRTC` 作为外部依赖注入（偏移 `547`），本项目 demo 侧实际安装 4.24.6，满足约束。

### 4.2 ⚠️ RTM 创建 StreamChannel 会改写全局 RTC 参数 — confirmed

偏移 `1197263` 一带（`StreamChannelImpl` 构造函数）：

```js
A.setParameter("ENABLE_DATASTREAM_2",!0),A.setParameter("DATASTREAM_MAX_RETRANSMITS",0),A.setParameter("AP_RTM",!0),this._context.rtmConfig.logUpload&&A.setParameter("UPLOAD_LOG",!0);
```

这里的 `A` 就是全局 `AgoraRTC` 模块。同一构造函数里还会按 **RTM 的** `logLevel` 调 `AgoraRTC.setLogLevel(...)`（偏移 `1196434`），以及在 `join` 时按 RTM 的 area 配置调 `AgoraRTC.setArea(...)`（偏移 `1198975` 之后）。

**后果**：只要用了 RTM Stream Channel，页面里**所有** `IAgoraRTCClient`（包括业务自己创建的音视频 client）都会被这些全局参数影响，其中 `DATASTREAM_MAX_RETRANSMITS=0` 和 RTC 日志级别被 RTM 的 `logLevel` 接管是最容易造成困惑的两项。这是 **实现层事实，官方文档未提示**。

若不使用 Stream Channel（只用 Message Channel / Presence / Storage / Lock），则不触发这些改写 —— 实测：仅构造 RTM 实例不产生任何 `AgoraRTC.setParameter` 调用。

### 4.3 RTC client 复用逻辑目前是死代码 — confirmed

同一处（偏移 `1197372`）：

```js
const r=[];this._isReuseRtcClient=r.length>0,this.log("Create streamChannel, isReuseRtcClient: ".concat(this._isReuseRtcClient)),this._rtcClient=this._isReuseRtcClient?r[0]:A.createClient({codec:"vp8",mode:"rtc"})
```

`r` 是硬编码空数组，故 `_isReuseRtcClient` **恒为 false**，每个 StreamChannel 必定 `createClient` 自建 RTC client。日志里 `isReuseRtcClient: false` 是预期值，不是异常。含义：N 个 StreamChannel = N 个额外 RTC client。

知识库 `content/stable/rtm-web-sdk-architecture.md:58` 与之一致：

> `createStreamChannel` 创建并缓存 `StreamChannel`。其 `StreamChannelImpl` 直接使用 AgoraRTC client 和 data channel

### 4.4 WebSocket 并发数：不是瓶颈 — confirmed

**每个 RTM 实例占 2 条 WebSocket**（双 env 架构）。`ConnectionController` 持有长度为 2 的数组（偏移 `504582`）：

```js
C(this,"curLoginSockets",[void 0,void 0]),C(this,"loginSocketSubs",[{receivers:[]},{receivers:[]}])
```

env 编号只允许 0/1（偏移 `460654`：`if(0!==e&&1!==e)throw new n_({ILLEGAL_RTM_ENV:...})`）。知识库 `content/stable/rtm-web-sdk-architecture.md:50` 印证：

> `Connection` 是资源层：持有 `AccessPoint` 和 env 0/env 1 两条 `Socket`

浏览器侧的权威限制：

**Chromium**（`net/socket/client_socket_pool_manager.cc`，我直接读取了 `chromium/chromium` main 分支源码）原文：

```cpp
// Default to allow up to 6 connections per host. Experiment and tuning may
// try other values (greater than 0).  Too large may cause many problems, such
// as home routers blocking the connections!?!?  See http://crbug.com/12066.
//
// WebSocket connections are long-lived, and should be treated differently
// than normal other connections. Use a limit of 255, so the limit for wss will
// be the same as the limit for ws. Also note that Firefox uses a limit of 200.
// See http://crbug.com/486800
std::array<size_t, kSocketPoolTypesSize> g_max_sockets_per_group =
    std::to_array<size_t>({
        6,   // kNormal
        255  // kWebSocket
    });
```

关键点：**WebSocket 不受那个众所周知的「每 host 6 条」限制**，走独立的 socket pool，每 group 上限 255。同文件的 pool 软上限为 256（kNormal / kWebSocket 各 256）。

配置代理时另有 per-proxy-chain 上限，且**两份来源数值不一致**：我直接读到的 `main` 分支为 `128, // kNormal / 128 // kWebSocket`，而另一路从 Debian 源镜像读取的 Chromium `151.0.7922.71` 为 `32 / 32`。这是版本差异还是读取差异**本次未能定论**（Chromium 官方源站 `chromium.googlesource.com` / `source.chromium.org` 在本环境被网络策略阻断，无法交叉核对）。可以确定的是：**一旦配置代理，实际天花板会显著低于 255**（32 或 128），具体数字需按目标浏览器版本自行核对，不要写死。

此外 Chromium 有一个**待握手连接**的节流器 `kMaxPendingWebSocketConnections = 255`（`services/network/websocket_throttler.h`），它只统计尚未完成握手的连接，握手完成即释放，因此不限制已建立的连接数；超限时以 `ERR_INSUFFICIENT_RESOURCES` / `"Insufficient resources"` 失败。同一 IP:port 的握手会按 RFC 6455 §4.1 串行化（`WebSocketEndpointLockManager`，解锁有 10ms 延迟），所以多实例**同时**登录时握手会被排队、略微拉长登录耗时。

**Firefox**（`modules/libpref/init/all.js`）原文：

```js
// the maximum number of concurrent websocket sessions. By specification there
// is never more than one handshake oustanding to an individual host at
// one time.
pref("network.websocket.max-connections", 200);
```

**Safari**：**未查到公开的连接数上限**。开源可及的 WebKit 代码（WebKitGTK / libsoup 后端）中没有相应上限；Apple 实际发货的 CFNetwork 后端不开源，因此既不能确认存在也不能排除。按「未说明」处理，不要假设无限。

**折算到本项目**：即使跑 10 个 RTM 实例也只是 20 条 WebSocket，距 Chrome 255 / Firefox 200 很远。**WebSocket 并发数不是本项目的瓶颈**，真正的约束是每实例的 CPU/内存、RTC 采集设备的独占性，以及服务端并发与计费。

### 4.5 已知的 RTM/RTC 共存排障口径 — confirmed

知识库 `content/stable/environment-evidence-matrix.md:47`：

> RTM 与 RTC 断连时间高度一致时，可把客户端运行时压力或主线程阻塞列为候选；时间不一致时优先继续查网络策略、AP/Link、token 或业务逻辑。时间对齐只是支持证据，不是单独根因。

这条对「单页跑多个真实端」很实用：多实例把主线程压力抬上去以后，RTM 与 RTC 同时断连的表现应先怀疑运行时压力，而不是网络。

## 5. 对本项目的影响

### 5.1 结论：单页面多实例可行，但必须满足两条硬约束

1. **每个真实客户端必须用不同的 `userId`**。同 `appId+userId` 的第二个实例在构造期就抛 `-10027`（1.2）。
2. **`userId` 在页面生命周期内不可回收**。因为注册表只 `add` 不 `delete`（1.3），一个 `userId` 用过之后，即使 `logout()` 也不能在同一页面里重建。

没有官方实例数上限（1.5），所以「语聊房 2 端、会议室/互动课堂更多端」在 SDK 层面**不需要**改成「1 真实端 + 其余模拟」。这一条直接解除了票里对 `08` 的悲观预设。真正需要按场景定上限的理由变成了运行时开销与设备独占，而不是 SDK 硬限制。

### 5.2 ⚠️ 当前代码里已经存在的一个 bug（与 1.3 直接相关）

`src/runtime/rtm/AgoraRtmAdapter.ts:43` 的 `connect()`：

```ts
async connect(credentials: RtmCredentials): Promise<void> {
  if (this.client) await this.disconnect();
  this.client = new AgoraRTM.RTM(credentials.appId, credentials.userId, { logLevel: 'warn' });
```

「先 disconnect 再 new 同一个 userId」正是 1.3 实测会抛 `-10027` 的路径。而 `src/app/ScenarioWorkbench.tsx` 的 `useEffect` 依赖里含 `session.roleId` 与 `connectionSettings`，**切换角色或改连接配置都会重跑这个 effect** → 第二次 `connect()` 用同一个 `settings.userId` → 抛 `-10027`。React 18 StrictMode 的双次挂载也会命中同一路径。

另外 `ConnectionDialog` 只提供**单个** `userId` 字段（`src/components/ConnectionDialog.tsx:8`），当前 real 模式实质上只支持一个真实端，还没有多端所需的 per-role userId 模型。

建议（不在本次改动范围内，留给 `08` / 后续实现）：

- 真实端的 `userId` 改为「基线 + 角色/实例后缀」派生（如 `${base}-host` / `${base}-audience-1`），保证同页唯一；
- 由于 uid 不可回收，**重连必须复用同一个 client 实例**（`login()` / `logout()` 可重复调用），而不是销毁后重建；如确实需要重建，必须换一个新的 `userId`（例如再挂一个自增后缀）；
- 把 `-10027` 显式纳入 `errorMap`，给出「该 userId 在本页已被占用」的可读文案，避免暴露为裸 SDK 错误。

### 5.3 嵌入清单（交给上层网站的对接要求）

上层 iframe 至少需要：

```html
<iframe src="https://<demo-host>/..."
        allow="camera; microphone"
        sandbox="allow-scripts allow-same-origin"></iframe>
```

- `allow-same-origin` **不可省**，否则 `login()` 会以 `SecurityError` 失败（3.2）。这是最容易被上层"出于安全"删掉、进而造成"demo 在你那能跑在我这不能跑"的一项，应写进对接文档。
- 跨域但未 sandbox 的 iframe 无需特殊处理（3.3）。
- CSP 的 `connect-src` 需显式列出 AP / edge / 上报域名，不要依赖 `'self'`（3.4、3.5）。
- 防火墙白名单以 3.5 为**候选清单**，生产前向 Agora 确认官方清单。

### 5.4 多实例场景的实现纪律

- **不要**用 `setParameter` / `setArea` 做 per-instance 配置 —— 它们是进程级全局（2.3）。per-instance 只有构造参数（`logLevel`、`presenceTimeout`、`cloudProxy` 等）。
- **不要**用 `IGNORE_DUPLICATE_USER_ID_ERR` 绕开 uid 唯一性（1.4）：它是 QA 参数，且绕过后的多实例互踢行为未验证。
- 每实例创建后**立刻**注册监听器再 `subscribe`。知识库 `content/resources/web-rtm-multi-instance-identification.md:47`：

  > 6. Integration rule: listeners before subscribe. 创建实例后尽早绑定监听器，避免订阅完成前后的快速事件丢失。

- 预期日志噪声：每个 `Ins#>1` 的实例都会打一条 error 级 `please pay attention to avoid mutual kick issues or client mix-up issues`（1.7），不要当故障处理，但也不要在演示时暴露给客户。
- 排障时按 `Ins#` 拆实例，但**不要**用 `Ins#` 的绝对值推断实例数量 —— 被嵌入时基数可能非 1（1.7）。
- 若某个场景要用 Stream Channel，注意它会改写全局 RTC 参数并新建 RTC client（4.2、4.3），需与 `07`（共享 `rtc.ts` 接口边界）一并设计。

### 5.5 仍需实测才能定的事

以下不能靠文档，必须在真实环境压：

- 单页可稳定运行的实例数（CPU / 内存 / 主线程阻塞），以及断连时的表现（4.5 给了判读口径）；
- 服务端对同 appId 大量并发 uid 的策略与**计费**影响（本次完全未涉及）；
- Safari 的 WebSocket 上限（4.4，未说明）；
- 多实例同时 `login()` 时因同 IP:port 握手串行化导致的登录耗时增长（4.4）。
