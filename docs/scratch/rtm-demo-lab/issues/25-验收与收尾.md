## Answer

### 规则一：零运行时依赖 —— 通过，且由测试守着

两份文件各 4 条 import，运行时只有 1 条：

```
import AgoraRTM from 'agora-rtm';                                  ← 唯一运行时
import type { RTMConfig, RTMEvents } from 'agora-rtm';
import type { SeatInvitation, VoiceRoomSnapshot } from './state';  ← 纯类型，编译后消失
import type { VoiceRoomStateAdapter } from './stateAdapter';       ← 纯类型
```

关键是**这条不靠人工核对守**。`rtm-host.test.ts` 与 `rtm-audience.test.ts` 各有一组 `describe('零依赖')`，用 `?raw` 读源码正则扫 `^import`（排除 `import type`）：相对路径必须为空数组、运行时 import 列表必须恰好 `['agora-rtm']`、不得出现 `'./transitions'` 的运行时 import。听众端另有一条「不得 import 房主端文件」。日后重构手滑会立刻红。

核对时我自己先踩了一次坑：grep 相对路径 import 会命中 4 条，看起来像违规，实际全是 `import type`。规则一的原文允许纯类型 import，所以这 4 条合规 —— 记在这里，免得下一个核对的人重复惊一次。

### 规则二：只有调用顺序、没有业务规则 —— 通过，有一处需要判定

逐个方法过了一遍两份文件。业务规则确实全在注入的 `stateAdapter.reduce` 里，RTM 文件只写「先抢锁 → 重读快照 → 过 reducer → 带 revision 写回 → finally 释放锁」这类顺序。

**需要判定的一处**：`approveSeatRequest` / `rejectSeatRequest` 里有

```ts
const request = this.snapshot.queue.find((item) => item.id === requestId);
if (!request) throw new Error('排麦申请不存在');
```

判定为**合规**。它查快照是为了拿到收件人 uid（下一步 `publishToUser(request.userId, ...)` 需要），属于「发消息得先知道发给谁」的编排前置，不是权限判断。「谁有权同意上麦」「什么状态能转 active」这类规则仍然在 `transitions.ts`。

判据留给后来者：**RTM 文件里读快照只允许用于取参数，不允许用于决定动作是否合法。** 前者去掉会导致代码跑不通，后者去掉只会让非法动作也发出去 —— 后者一旦出现就是违规。

`handleMessage` 的 `default` 分支也确认了同一原则：`seat.request` / `seat.media-ready` 这类消息**不做本地推断**，权威状态一律等 Storage 事件，注释里写明了理由。

### 规则三：RTC 例外的理由两处都写了 —— 通过

- `src/shared/rtc.ts` 顶部有专门一节「为什么这个文件可以被各场景 import（零依赖铁律的唯一例外）」，给了三条判据（不是要展示的东西、没有场景差异、不采集 trace），并明确写了 **「不要把这条例外推广成『可以再抽一个共享层』」**，判据是三条同时成立。
- README 有独立一节「为什么 RTM 一角色一份、RTC 共享一份」，含教材 / 脚手架的对照表。

两处都还写明了「音频内部播、视频交出 track」这个刻意的不一致及其理由，防止被顺手统一。

### 验收锚点「第二个场景一天产出」：**没有实测，只有间接证据。如实记录**

**这条锚点在本 effort 里从未被真正验证过** —— 我们只实现了一个场景，第二个场景一行没写。票 19 记录的是「听众端由房主端复制改造而来」，那是**同一场景内的第二个角色**，不是第二个场景。这两件事的工作量差别很大，不能互相代入。

能提供的间接证据只有复制比例。把两份 RTM 文件的角色名归一（`host` ↔ `audience` 等）后比对：

| 指标 | 数值 |
| --- | --- |
| 归一后完全相同的行 | 852 |
| 房主端独有 | 219 行 |
| 听众端独有 | 270 行 |
| 可复制比例（相同 / 听众端 1122 行） | **75.9%** |

票 19 报的是 84.1%（635 / 755，只数代码行、不含注释与空行）。我这次连注释一起数，得到 75.9% —— 差异来自注释：两份文件的文件头注释与方法注释是各写的，这部分不可复制。**两个数都对，量的不是同一个东西**；引用时要说明口径。

推论只能到这一步：**角色层面的复制成本已知很低（约八成可复制），场景层面的复制成本未知。** 一个新场景要新写的是注册表条目、`state.ts`、`transitions.ts`、`stateAdapter.ts`、场景容器与展示组件，以及两份 RTM 文件里那两三成的语义方法。语聊房这一套非测试代码 4462 行、含测试 8105 行，其中外壳 1700 行不用动。

**给用户的建议**：不要把「一天」当作已验证的事实写进对外材料。它现在是**设计目标**，不是实测结论。第一个真实数据点只能等下一个场景实现时产生 —— 建议实现下一个场景时**记录实际耗时**，再回来修订这条锚点。如果那时明显超出一天，需要重新权衡的是模板化程度，而**不是**去抽 RTM 共享基类（规则一与规则三已经把那条路封掉了，理由在 spec 与两处注释里）。

### 顺带发现并修掉的一件事（票 24 期间）

调研笔记 `docs/research/2026-08-05-rtm-web-多实例与嵌入约束.md` 里的 bundle 字符偏移量是在 `2.3.0-beta.0` 上算的，而 vendor 里是 `2.3.0` 正式版。实测两版偏移相差数十到数百字节：

| 锚点 | beta.0 偏移 | 正式版实际 | 差 |
| --- | --- | --- | --- |
| `cf` 声明（重复 uid 注册表） | 434726 | 434780 | +54 |
| 构造期重复检查 | 434992 | 435014 | +22 |
| 错误码定义 | 66191 | 66167 | −24 |
| 默认端口表 | 120494 | 85687 | −34807 |
| `banOriginEventListener` | 178358 | **找不到** | — |

**结论本身没有受影响** —— 关键锚点都在正式版上复核过内容一致（重复 uid 注册表仍然只 `add` 不 `delete`、`-10027` 仍在、事件仍按实例隔离）。但复现命令里的数字不能直接用了。票 24 已在笔记开头加了警示段落，**没有重新计算全部偏移**（成本与收益不成比例），记入未决第 14 条。

这件事的教训值得留下：**给压缩 bundle 的字符偏移量是版本脆的引用方式**，换一个 patch 版本就全部失效。下次做这类调研，除偏移量外应同时给一段**可 grep 的特征字符串**，那个跨版本稳定得多。
