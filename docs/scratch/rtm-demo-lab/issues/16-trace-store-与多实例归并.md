# 16 — trace store 与多实例归并

**Blocked by:** 12

**Status:** resolved

**What to build:** 时间线的数据层——单实例的 trace 采集容器，以及把多个实例的 trace 按时间归并成一条时间线的能力。这是 23 个场景共用的样板，值得单独一票做扎实。

trace 容器导出为可订阅对象而非裸数组：时间线是本 demo 的核心展示物，「API 被调用的瞬间节点就出现」值得那点订阅样板，React 侧配外部 store 订阅即可，无需轮询与整数组 diff。

- [x] 单实例环形上限 500 条，超出静默丢弃**最旧**的
- [x] 没有任何「已截断」标记条目——静默丢弃
- [x] 订阅者在每次写入后被调用
- [x] 取快照返回的数组被改写不影响 store 内部状态
- [x] 上限值是模块常量，客户拷走后可自行调整
- [x] 两份 trace 按时间戳归并成一条时间线
- [x] 同毫秒时按各实例内部的单调递增序号做稳定排序
- [x] 归并后每条仍带自己的 uid 与角色——**来源不能丢**（uid 与角色由实例自己贴，不由业务层读取时补）

条目类型只有「API 调用」与「收到事件」两种，对应原始需求：调 RTM API 出一个节点，收到 RTM 事件出一个节点。

**注意：** 这份 store 放在共享目录只是为了给测试和归并模块提供类型与参考实现。两份可拷走的 RTM 文件**各自内联自己的 store 实现**，不 import 它。这不是重复的疏漏，是零依赖的代价。

## Answer

两个模块，23 个测试（store 15 + 归并 8）。

| 文件 | 职责 |
| --- | --- |
| `src/shared/timeline/traceStore.ts` | 单实例采集容器，可订阅 |
| `src/shared/timeline/mergeTraces.ts` | 多实例按时间归并 |

### 条目字段

`seq`（实例内单调递增，从 1 开始）、`at`（时间戳，归并主键）、`kind`（只有 `api` / `event`）、`role`、`uid`、`name`，可选 `summary` / `durationMs` / `errorCode` / `errorMessage`。

**`uid` 与 `role` 由 store 在写入时贴**，调用方只传业务字段 —— 归并后来源不能丢，不能让业务层读取时再补。

### 环形上限

`TRACE_LIMIT = 500` 作模块常量导出，客户拷走后可自行调整。构造参数也允许覆盖（测试用小上限跑得快）。

超限静默丢弃最旧，**不插入任何"已截断"标记条目**。有一条专门的测试遍历全部条目，断言每一条都是真实采集的 `api`/`event`、名字符合真实调用的模式 —— 合成的提示条目会被抓出来。丢弃不影响 `seq` 继续单调递增。

### 快照的两个冲突约束

`getEntries()` 要同时满足：

1. 未写入时返回**同一引用** —— `useSyncExternalStore` 的硬要求，每次新建数组会让它判定"变了"而无限重渲染。
2. 调用方改写返回值**不得影响内部状态**。

实现是记忆化 + 长度校验：快照缓存起来，发现长度与内部数组不一致就重建。

**已知局限**：这挡得住 `push` 与 `length = 0`，挡不住原地替换元素（`snapshot[0] = x`）。彻底的办法是 `Object.freeze`，但冻结会让改写**抛错**，而本票的验收项要求的是"改写不影响内部状态"即静默无效。两者不可兼得，取了静默无效。若后续发现原地替换真的发生，改用 `structuredClone` 或冻结并接受抛错。

### 归并

按 `at` 升序，同毫秒用 `seq` 稳定次序。不改写入参数组（先展平再排序）。

支持任意份数而非固定两份 —— 课堂是老师 + 学生 + 助教三端，会议室是主持人 + 参会者，spec 的角色数按场景变化。有一条三端测试盯住这点。

### 零依赖的代价

这份 store 放在 `shared/` 只是给测试与归并模块提供类型和参考实现。**两份可拷走的 RTM 文件各自内联自己的 store 实现，不 import 它。** 这不是重复的疏漏，是零依赖铁律的代价 —— 客户拷走 `rtm-host.ts` 时不能要求他一并拷 `shared/`。

模块头部注释写明了这一点，防止后来者"顺手消除重复"。
