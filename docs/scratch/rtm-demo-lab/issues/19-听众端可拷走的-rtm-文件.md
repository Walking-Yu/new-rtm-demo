### 听众端与房主端的四处真实差异

除语义方法清单不同，机制上只有四处不一样，其余全是刻意重复：

| 差异 | 听众端的做法 |
| --- | --- |
| 初始快照 | **不写。** 房间由房主创建；听众只读，读不到就保持占位快照等 Storage 事件补 |
| 治理命令 | **收，不发。** 收到强制静音／强制下麦／踢出／封禁后**回 ack** |
| 自己的静音与下麦 | **不需要 ack** —— 对自己的操作，没有对端要确认 |
| 封禁检查 | 连接时发现自己在封禁名单里直接失败退出 |

因此听众端**没有** `ackTimers`（那是发命令方才需要的），而多了 `sendExecutedAck()`。

### 一个实现时才浮现的顺序约束

**踢出与封禁必须先回 ack 再退出。** 反过来的话连接已断，ack 发不出去，房主那边必然超时报错。这条不在 spec 里，是写测试时撞出来的，已用测试锁住。

### 语义方法清单（听众端 11 项，对齐 spec）

`connect` / `disconnect` / `requestSeat` / `cancelSeatRequest` / `acceptInvitation` / `rejectInvitation` / `setOwnMuted` / `leaveOwnSeat` / `sendChatMessage` / `sendEmoji` / `sendGift`，外加媒体结果驱动的 `activateOwnSeat` / `rollbackOwnSeat`，以及执行房主命令并回 ack 的 `applyForcedMute` / `applyForcedLeave`。

### 零依赖已核验

## 重复率 84%，超过票里写的 60% 阈值 —— 已上报，用户裁决为「接受」

测量方法：按行做集合交集（`difflib` 同款口径），分别统计含注释与仅代码两种。

| 口径 | 共同行 | 听众端总行 | 重复率 |
| --- | --- | --- | --- |
| 含注释 | 899 | 1122 | **80.1%** |
| 仅代码（去空行与注释） | 635 | 755 | **84.1%** |

spec 的 Further Notes 第 4 条预估「约 250 行重复」、并写明「若远超预期（比如超过文件的 60%），回头讨论**是否用代码生成而非抽象**来解决，但不要抽共享基类」。

实测 635 行代码重复，是预估的 2.5 倍。**原因不是实现走偏，而是预估偏低**：spec 把「连接、订阅、信封、去重、mutate、trace、重连」列为重复项时没有计入它们各自的完整体量 —— 单是 `mutate()` + `acquireRoomLock()` + 信封解析 + trace store 内联就已接近 400 行，而这些恰恰是「客户要拷走的 RTM 机制精华」，按设计就该在两份文件里各存一份。

三个可选方向（**都不涉及抽共享基类**，那条被 spec 明令禁止）：

1. **接受现状，写进 README 与编写规程。** 重复是「可单文件拷走」的直接代价；两份文件各自自洽、客户拷一个就能跑。维护成本用「改动清单」控制：连接／订阅／信封／去重／mutate／trace／重连七段改动时必须同步两份，测试各自锁住行为，改漏会红。
2. **改用代码生成。** 写一份骨架模板 + 每角色一份差异描述，构建期生成两份 `rtm-<role>.ts`。产物仍是零依赖单文件，客户拷走体验不变；代价是仓库里多一层生成器，且「打开文件就能读懂调用顺序」的教材属性要靠生成产物入库来保住。
3. **维持现状但补一个一致性测试。** 用测试断言两份文件的共同段落逐字一致（把重复变成机器可验证的约束），改漏一处就红。介于 1 和 2 之间，不引入生成器。

### 裁决结果：方向 1（接受重复，代码不动）

用户选择**接受重复、不引入代码生成、代码一行不改**。理由与遗留风险已写进 spec 的「为什么接受 84% 的重复」一节，Further Notes 第 4 条同步划掉标记已结。

不引入生成器的核心理由：生成器要么让人去读模板而不是读成品文件（教材属性没了），要么让人怀疑成品与模板是否同步（自洽性没了），两者都比「改动时要改两处」更贵。

遗留风险只有一个 —— **七段共同机制改动时改漏一处**。当前由两份文件各自的完整测试覆盖挡住（房主端 74 个、听众端 72 个），改漏就红。方向 3（共同段落逐字一致的一致性测试）本阶段不做，已记入 spec 未决项，若日后发现测试覆盖不足再补。
