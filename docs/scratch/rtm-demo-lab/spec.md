## 2026-08-18 语聊房覆盖决策

语聊房的最终建造依据已更新为 [`语聊房页面初始化-api-备忘录-最新.md`](./语聊房页面初始化-api-备忘录-最新.md) 与实现票 41–49。本 spec 中与以下决策冲突的早期段落只作历史背景，不再是语聊房的验收依据：

- 每个 Tab 只运行一个角色和一个页面级 RTM client。
- 房间目录与封禁只存于 Local Storage，URL 只使用一个 `data` Base64URL payload。
- 房间 Storage 只含 `hostUserId`、`announcement`、`seats`、`forcedMutedUserIds`，不使用 Lock、管理员/排麦额外频道或主动 `getChannelMetadata()`。

- 麦位只表达归属，RTC 失败不回滚麦位。

## 2026-08-26 默认 HTTPS 启动契约

### 目标

本地开发者直接运行 `./start-demo.sh` 时，应得到一台可供同一局域网其他设备访问的 HTTPS 开发服务器，不再需要记忆 `RTM_DEMO_HOST=0.0.0.0`、`--https` 和 `--no-open` 三项额外配置。默认行为必须完整等同于：

```bash
RTM_DEMO_HOST=0.0.0.0 ./start-demo.sh --https --no-open
```

默认服务只监听 HTTPS `8080`，监听地址为 `0.0.0.0`，启动后不自动打开浏览器。脚本继续自动发现一条非内部局域网 IPv4 地址，将该地址写入本地开发证书，并在日志中打印远端设备可访问的完整 HTTPS URL。

### 命令契约

| 命令 | 协议与端口 | 默认监听地址 | 自动打开浏览器 |
| --- | --- | --- | --- |
| `./start-demo.sh` | HTTPS `8080` | `0.0.0.0` | 否 |
| `./start-demo.sh --https` | HTTPS `8080` | `0.0.0.0` | 否 |
| `./start-demo.sh --http` | HTTP `8080` | `0.0.0.0` | 否 |
| `./start-demo.sh --both` | HTTP `8080` + HTTPS `8443` | `0.0.0.0` | 否 |

`--https` 保留为显式且向后兼容的 HTTPS-only 入口。新增 `--http`，确保默认模式改为 HTTPS 后，普通 HTTP-only 开发入口仍然存在。`--both` 继续同时启动两个服务。`--no-open` 保留为兼容参数；因为所有模式默认都不打开浏览器，所以它不再改变行为，也不得报错。

本次不新增 `--open`。需要打开页面时，开发者使用启动日志打印的 URL；是否增加显式自动打开能力，留到出现真实需求后再设计。

### 环境变量覆盖

默认值变化不改变现有环境变量的优先级。显式传入的 `RTM_DEMO_HOST`、`RTM_DEMO_PUBLIC_HOST`、`RTM_DEMO_PORT` 和 `RTM_DEMO_HTTPS_PORT` 继续覆盖脚本默认值。

其中 `RTM_DEMO_HOST` 控制 Vite 监听地址，缺省为 `0.0.0.0`；`RTM_DEMO_PUBLIC_HOST` 控制证书包含的 IPv4 地址和启动日志中的访问地址，缺省由脚本自动发现。两者职责保持分离，避免把 `0.0.0.0` 当作用户实际访问地址写入 URL。

### HTTPS 证书与失败行为

HTTPS 默认化不改变安全约束：脚本可以调用 `mkcert` 生成本地证书，但不得自动安装根 CA。首次使用者必须自行安装 `mkcert` 并明确执行 `mkcert -install`；远端电脑或手机也必须安装并信任启动日志所指向的 `rootCA.pem`。

缺少 `mkcert` 时，默认启动应立即失败，打印安装与信任提示，不得静默降级到 HTTP。证书和私钥继续只写入被 gitignore 的 `.cert/`；可以向远端设备分发 `rootCA.pem`，不得分发 `rootCA-key.pem` 或开发服务器私钥。局域网 IPv4 发生变化后，重新启动脚本以生成包含新地址的证书。

### 文档与测试验收

启动脚本帮助信息、环境检查输出、README 常用命令以及 agent 项目约定必须同步反映新默认值。`AGENTS.md` 与 `CLAUDE.md` 修改后必须保持逐字一致。

测试先固定以下行为，再修改脚本：

1. `--help` 将默认 URL 描述为 HTTPS `8080`，并列出 `--http`、`--https`、`--both` 和 `--no-open`。
2. 脚本源码的默认模式是 HTTPS、默认监听地址是 `0.0.0.0`、默认不打开浏览器。
3. HTTP-only、HTTPS-only 和双服务三种显式模式仍可选择。
4. 现有证书生成、单入口构建和 E2E 环境隔离契约不发生变化。
5. agent 双入口同步测试通过，证明 `AGENTS.md` 与 `CLAUDE.md` 逐字一致。

### 非目标

本次不让启动脚本读取 `.env.local` 中的 shell 变量；该文件仍由 Vite 用于 `VITE_APP_ID` 等前端配置。本次也不自动安装 CA、不处理公网暴露或路由器端口映射、不修改生产部署方式，并且不改变 `npm run dev` 与 `npm run dev:https` 的底层职责。

## Problem Statement

想接入声网 RTM 的开发者在文档站上看不到 RTM 究竟能做什么。文档按 API 组织，读完知道有 Message、Presence、Storage、Lock 四类能力，但不知道"一个语聊房的上麦流程该按什么顺序调这些 API"。

现有的 demo 也帮不上：它们要么是单一场景的完整应用（读者得先理解整个工程结构才能找到关键那几行），要么是纯前端模拟（点得动但没有真实链路，看不到 API 调用与事件的因果）。结果是开发者评估阶段无法快速判断 RTM 是否覆盖自己的业务，进入实现阶段后又得从零摸索调用顺序。

对声网侧还有第二个问题：每新增一个场景演示的成本太高，导致场景覆盖长期停在个位数，无法展示 RTM 的业务广度。

## Solution

一个挂在文档站里的 RTM 能力演示实验室，读者不用离开文档站、不用填表、不用注册就能玩。

顶部是**场景地图**：8 个业务分类、23 个具体场景全部可见可点，读者一眼看到 RTM 能覆盖的业务面。点进任一场景，主区是一个**真实连着 RTM 的演示**（本阶段只有语聊房是真的，其余 22 个是写明计划的路线图占位页）。

主区右侧是一条**时间线**，把当前页面的 RTM API 调用和 RTM 事件按时间串起来，读者点一次“申请上麦”就能看到本端调用、服务端回流事件、顺序和耗时。这是本产品的核心展示物 —— 它把“RTM 怎么用”从文字变成可观察的因果链。

语聊房每个浏览器标签页只运行**一个角色和一个真实 RTM client**。Host 与 Audience 的真实联调使用两个标签页；每个页面只展示本角色视角和本页面的数据流。

实现分为三个 seam：应用级 `app-rtm.ts` 与语聊房单页面应用生命周期对齐并持有唯一 SDK client；Host/Audience 各自的 `rtm.ts` 暴露按功能命名的原子 RTM 操作，同角色 `onRtmEvent.ts` 负责事件绑定和协议校验；`event-driven-single-room-client.ts` 是当前 Tab 的业务 store，负责状态、toast、RTC 和后续动作。

**验收锚点：第二个场景能靠复制语聊房样板在一天内产出。** 这条决定了下面所有"模板化"的设计取向；任何提升单场景质量但拖慢复制速度的做法都要重新权衡。

## Implementation Decisions

### 三条不可越界的规则

这三条是整套设计的地基。实现时任何一处违反都要停下来讨论，**不要"顺手统一"**。

**规则一：每个 Tab 只有一个角色和一个应用级 RTM client。** `AppRtmSession` 与语聊房单页面应用生命周期对齐并在 login 前注册事件，当前角色通过自己的 `rtm.ts` 与 `onRtmEvent.ts` 使用该会话。

**规则二：`rtm.ts` 只提供按功能命名的原子 RTM 操作，`onRtmEvent.ts` 只提供事件协议入口。** 两者都不得维护 nickname、麦位、公告、排麦队列或 RTC 状态；业务消费只在 `event-driven-single-room-client.ts`。

**规则三：不同角色之间不共享 RTM 运行时基类。** 房主和听众各有自己的 `rtm.ts` 与 `onRtmEvent.ts`，允许刻意重复；页面会话和 RTC helper 是场景级共享 seam。

### 刻意接受的重复

房主端与听众端各自保留订阅、消息信封、Presence、trace 和事件过滤机制；最终协议不使用 Lock、额外 Message Channel 或主动拉取。

**接受角色之间的重复，不抽共享层。** 客户复制一个角色 bundle 后即可独立修改；代价是共同机制变更时要同步两个角色的 `rtm.ts`，由两边等价的契约测试约束。

这条同时决定了文件数按角色种类增长，不按在线人数增长；每个标签页只实例化自己角色的模块。

拆分目标不是消除所有重复，而是让传输、事件入口和业务状态各自局部化。共同机制改动时由两边等价的契约测试约束，源码边界测试阻止业务概念反向渗入角色 RTM 模块。

### 环境配置契约

**只有 appId 一个字段。** 不加区域（两站各部署一份，区域由"部署了哪一份"决定）、不加日志级别、不加场景白名单（可见性是注册表状态字段的职责）。字段集要扩展等到有真实需求，不预留。

优先级链是三层：全局注入变量（线上，最高优先级）→ 构建期环境变量（本地兜底）→ 都缺失则渲染引导页（不是报错页）。

**全局注入必须能覆盖构建期环境变量。** 后者是构建期烧进 bundle 的常量，若让它优先，上层网站永远换不掉 appId。

**源码里没有第三层硬编码兜底。** 真实 appId 只进被 gitignore 的本地环境变量或部署环境注入，不进入 `index.html` 和源码。若写成源码常量，删除配置后 demo 仍能跑，注入契约就失去约束力，也会把项目标识暴露到开源仓库。

**要求同步注入，启动时读一次快照。** 上层页面必须在加载 bundle 之前写好全局变量。配置模块在加载时解析一次存进常量，**不监听后续变化、不轮询、不代理劫持全局对象**。支持异步注入意味着要引入"等待配置"的加载态、以及注入迟到时已建立的 RTM 连接如何重连 —— 收益不成比例。这条要求写进 README 的注入契约一节。

### 身份推导

主页提供 Host 创建和 Audience 邀请输入。URL 只有一个 `data` Base64URL 参数，携带角色、页面 UID、nickname 和单个本地房间目录项；刷新和分享都复用同一 codec。每个标签页只推导一个页面 UID，并创建一个 `AppRtmSession`。

### 路由

路由形如"一级分类 / 二级场景"。渲染前先过配置判定：未配置则渲染引导页，不进场景。

场景 id 用 kebab-case、**不带一级分类前缀**（`voice-room` 而非 `social-voice-room`）—— id 出现在 URL 里应当稳定，前缀会在场景归类调整时造成 id 变更。

### 场景注册表

8 个一级分类：社交、教育、企业、物联网、内容、医疗、出行、游戏。

二级条目**只有 4 个字段**：id、标题、一句话摘要、状态。从遗留场景目录明确丢弃的字段及理由：

| 丢弃字段 | 理由 |
| --- | --- |
| 画布类型 | 服务于"一套通用 UI 数据驱动渲染 24 个场景"，与"一场景一套角色业务 bundle + 独立主容器"正面冲突 |
| 初始状态 / 动作 / 后继状态 / 事件文案 / 语气 | 假状态机，是模拟层的输入。留着会诱导后来者继续写模拟 |
| 是否支持真实 RTM | 新架构下已实现的场景都是真的，未实现的用状态字段表达 |
| 角色清单 / 能力标签 | **不进注册表但不丢弃** —— 归档为实现资料，由后续每个场景的 effort 取用 |

状态字段**只有"已实现"和"已规划"两个值**。不引入"进行中" —— 它是过程状态，会诱使人把半成品合进主干；一个场景要么可点进去玩，要么标明未建。

本阶段唯一"已实现"的是语聊房（归社交），由遗留的两个语聊房场景合并而来。其余 22 个"已规划"。

**已规划场景的表达：tab 可见、可点、进去是统一占位页**，写明该场景计划演示哪些 RTM 能力并指向语聊房。不灰置（客户会以为坏了）、不隐藏（违背"让客户看见 RTM 能覆盖多少场景"的展示目的）。23 个 tab 本身就是在说"RTM 能做这些"，占位页把"未实现"变成"路线图"。

### 角色业务 bundle 的契约

`AppRtmSession` 在 `login()` 前注册 `linkState`、`message`、`presence`、`storage`、`token` 五类 listener，页面生命周期内只创建一个 SDK client。离开房间只 `unsubscribe()`，场景真正卸载才 `logout()`。

Host/Audience `rtm.ts` 只依赖页面级操作 seam，不创建 SDK client、不 login/logout、不主动读取 Storage。它们对业务层暴露按功能命名的语义函数，固定消息 type、metadata key、Presence 字段和 trace；通用 publish、Presence/Storage 写入只作为私有实现。

Host/Audience `onRtmEvent.ts` 绑定当前角色事件，负责房间过滤、信封校验、TTL、目标校验、去重和事件 trace，再调用业务 store 提供的 listener。它不维护 nickname、麦位、公告或 RTC 状态。

`event-driven-single-room-client.ts` 是当前 Tab 的唯一业务 store。它解析四个 Storage key、维护 Presence nickname/在线状态、驱动 RTC、生成 toast/系统消息，并可通过角色 `rtm.ts` 的语义函数触发后续 RTM 动作；不得直接调用 Agora SDK。

### 角色 RTM 机制

**消息封装、TTL 与去重。** 每条 RTM 负载使用包含协议版本、消息 id、房间、可选目标、发送时间、过期时间和 payload 的信封，默认 TTL 15 秒。接收路径固定为：校验上下文和信封 → 去重 → 记录 trace → 调用业务 `consume`。最终协议不自动重试。

**Storage 全量事件。** Channel Storage 只有 `hostUserId`、`announcement`、`seats`、`forcedMutedUserIds` 四个 key。Host 只在空 `SNAPSHOT` 上用该快照的 `majorRevision` 初始化；其他 `SNAPSHOT` / `UPDATE` 都是完整最新状态。Audience 不写 Storage，双方都不使用 Lock 或 `getChannelMetadata()`。

**Presence 是 nickname 与成员状态的唯一来源。** `SNAPSHOT` 全量替换在线 UID、nickname、`muted` 和 `microphoneError` store，增量事件处理 join/leave/timeout/state change/interval。缺少 nickname 或成员离线时，展示层降级为省略后的 UID，不读取 Storage `seat.displayName`。

**重连只消费 SDK 后续全量事件。** 不重复订阅、不主动拉取、不重放历史消息。

### 麦位归属与 RTC 发布解耦

麦位只表达归属：空位或被某个 UID 占用。房主批准申请或听众接受邀请时直接写入占用麦位；RTC 发布成功或失败均不改变麦位，用户可在保持麦位期间反复发布或取消发布媒体。静音是 Presence State 中的终端状态，不是麦位状态。

### trace 数据模型

每条 trace 条目的字段：实例内单调递增序号（归并时作同毫秒的稳定次序）、时间戳（归并主排序键）、类型、角色、uid、名称（API 方法名或事件名）、可选的短摘要（不放完整对象）、可选耗时（仅 API）、可选错误码与错误信息（仅 API）。

类型**只有两个值**：调 RTM API 出一个 api 节点，收到 RTM 事件出一个 event 节点。

**uid 与角色由实例自己贴**，不由业务层读取时补 —— 归并后来源不能丢。

导出为**可订阅对象**而非裸数组：时间线是本 demo 的核心展示物，"API 被调用的瞬间节点就出现"值得那约 25 行订阅样板；视图层配标准的外部 store 订阅钩子，无需轮询与整数组 diff。读取接口返回只读快照，业务层不得改写。

页面生命周期内 trace 只追加，不自动截断；只有用户点击“清空”或场景真正卸载才清除。

### 归并与筛选

归并模块订阅页面级 trace 与页面生命周期内累计出现过的角色 trace source，按时间戳归并，同毫秒用实例内序号作稳定次序。

面板支持 uid、角色、类型筛选。筛选是纯 UI 层过滤，不影响 trace 采集；被筛掉的条目仍在 store，取消筛选即恢复。

保留清空与折叠；不展示自动截断提示，因为正式实现不自动截断。

时间线**只呈现 RTM**，RTC 层不采集 trace —— 混入 RTC 节点会稀释"RTM 数据流"这条主线。若实测发现看不懂中间发生了什么，再考虑加一类媒体节点（记入未决，不在本文定）。

### 共享 RTC 辅助模块

全场景共享单份，只做四件事：加入频道、开关麦、开关摄像头、订阅远端。对外提供注册事件、加入、离开、发布与取消发布麦克风、设置麦克风静音、发布与取消发布摄像头、设置摄像头静音、取本地视频轨道这些能力；事件回调覆盖连接状态、远端音频发布状态、远端视频轨道、音量。

token 字段**从签名去掉**（默认无 token 鉴权），现有的可选 token 参数是要删的历史包袱。**屏幕共享不做** —— 会把 RTC 从辅助扩成一等能力。

**只有实际开音视频的用户创建 RTC 实例。** 多用户场景只允许一人开麦开摄像头，所以同一时刻页面内通常只有 1 个 RTC 客户端。

**音频内部直接播，视频交出轨道。** 这个不一致是刻意的，要在模块顶部注释写明理由，避免后人"统一"掉：音频没有渲染位置，交出轨道只会让业务层多做无意义的事；视频在视图框架下容器挂载时机与播放时机有竞态，交出轨道让组件在自己的副作用里对自己的 ref 播放才做得干净，这也是官方示例的写法。

远端视频轨道生命周期跨模块边界，约定：**远端取消发布或本端离开时，先以空轨道通知 UI 停播，再做取消订阅。** 顺序反了会导致 UI 播放已销毁的轨道。

**"只有一人开音视频"的约束落在模块层，不只靠 UI。** 模块内部维护单实例语义：已有实例时再次加入先离开（现有实现已是这个行为，保留）。UI 层同步灰置非持有者的开关并给出原因文案，而不是静默禁用。客户拷走这个模块后 UI 是他自己的，所以约束不能只在 UI。

现有 RTC 层两处裸抛的用法错误统一走归一后的错误类型，便于业务层区分"用法错误"与"SDK 错误"。

**摄像头相关能力是新增，不是迁移** —— 现有 RTC 层是纯音频的，收到远端发布时对非音频轨道直接丢弃。

## Testing Decisions

**什么是好测试：只测外部可观察行为，不测实现细节。** 本项目的具体判据是断言"对 SDK 发出了哪些调用、按什么顺序"，而不是断言内部字段或私有方法被调用过。

角色 RTM 测试使用应用级 RTM port 替身记录 subscribe、publish、Presence 和 Storage 原子调用；业务 store 测试通过 App RTM 事件 listener 驱动完整状态变化。两者都不发网络请求。

应用级 `AppRtmSession` 接受 SDK client factory；场景渲染测试使用 `testing.ts` 提供的 App RTM/RTC/Storage 无网络替身。

**要测的模块与重点：**

- 两份角色 `rtm.ts`：语义函数到 publish/Presence/Storage primitive 的固定映射、信封创建、订阅回滚和 trace。
- 两份 `onRtmEvent.ts`：房间/目标/TTL/去重校验、先 trace 后 consume、无业务状态。
- 单角色业务 store：Storage 全量替换、Presence 全量/增量、nickname 唯一来源、RTC 与治理顺序。
- trace store：只读快照、订阅通知和显式清空。
- 归并模块：同毫秒的稳定次序、归并后来源字段不丢。
- 时间线面板：两类节点的视觉区分与图例、三维筛选、取消筛选后条目恢复（证明筛选没动 store）、无截断提示。
- 场景注册表：分类与场景清单、**断言条目没有多余字段**（这是防止已丢弃字段被顺手加回来的护栏）、状态取值范围。
- 外壳与路由：已实现场景进真实演示、已规划场景进占位页、已规划场景的 tab 可点不灰置、配置缺失渲染引导页。
- 共享 RTC 辅助：单实例语义（重复加入先离开）、音频内部播与视频交出轨道的差异、远端取消发布时先通知停播再取消订阅的顺序、未加入就发布抛归一后的错误。
- 语聊房主容器：单角色准入、严格模式下重复挂载不泄漏连接、麦位归属不因媒体失败回滚、耳机告警与生产边界表述正确。

**端到端测试用占位 appId，刻意不验证真实连通性。** 覆盖场景地图、两级 tab、占位页、单角色语聊房、时间线、配置缺失引导和控制台错误。全部无头运行。

**完整真实链路仍需有效凭证人工验收，且必须戴耳机。** 自动化测试刻意不覆盖这一层。

测试文件与源码同目录、以 test 后缀命名，沿用现有的测试框架与断言库组合。
