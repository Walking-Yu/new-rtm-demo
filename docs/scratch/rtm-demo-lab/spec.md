## Problem Statement

想接入声网 RTM 的开发者在文档站上看不到 RTM 究竟能做什么。文档按 API 组织，读完知道有 Message、Presence、Storage、Lock 四类能力，但不知道"一个语聊房的上麦流程该按什么顺序调这些 API"。

现有的 demo 也帮不上：它们要么是单一场景的完整应用（读者得先理解整个工程结构才能找到关键那几行），要么是纯前端模拟（点得动但没有真实链路，看不到 API 调用与事件的因果）。结果是开发者评估阶段无法快速判断 RTM 是否覆盖自己的业务，进入实现阶段后又得从零摸索调用顺序。

对声网侧还有第二个问题：每新增一个场景演示的成本太高，导致场景覆盖长期停在个位数，无法展示 RTM 的业务广度。

## Solution

一个挂在文档站里的 RTM 能力演示实验室，读者不用离开文档站、不用填表、不用注册就能玩。

顶部是**场景地图**：8 个业务分类、23 个具体场景全部可见可点，读者一眼看到 RTM 能覆盖的业务面。点进任一场景，主区是一个**真实连着 RTM 的演示**（本阶段只有语聊房是真的，其余 22 个是写明计划的路线图占位页）。

主区右侧是一条**时间线**，把演示过程中每一次 RTM API 调用和每一个 RTM 事件按时间串起来，读者点一次"申请上麦"就能看到两端各发生了什么、顺序如何、耗时多少。这是本产品的核心展示物 —— 它把"RTM 怎么用"从文字变成可观察的因果链。

语聊房在一个浏览器标签页里同时跑**房主端和听众端两个真实客户端**，两台手机外框并排显示。读者不需要找人配合，一个人就能完整走通申请上麦、房主审批、静音、踢人这些双向流程，并在时间线上看到两端的交互。

对进入实现阶段的开发者，每个角色的全部 RTM 用法收在**一份零依赖的单文件**里（`rtm-<role>.ts`，如语聊房的 `rtm-host` 与 `rtm-audience`）。这个文件只 import RTM SDK 本身和纯类型，可以整份拷进自己项目直接用 —— 不需要连带拷任何工具模块。

**验收锚点：第二个场景能靠复制语聊房样板在一天内产出。** 这条决定了下面所有"模板化"的设计取向；任何提升单场景质量但拖慢复制速度的做法都要重新权衡。

## Implementation Decisions

### 三条不可越界的规则

这三条是整套设计的地基。实现时任何一处违反都要停下来讨论，**不要"顺手统一"**。

**规则一：角色 RTM 单文件零 runtime 依赖。** 每份 `rtm-<role>.ts` 只允许 import 两类东西 —— RTM SDK 本身，以及纯类型（编译后消失的类型导入）。不允许 import 任何共享模块，也不允许 import 同目录的转移函数模块（它以构造参数注入）。理由：这个文件是要被客户单文件拷走的教材。

**规则二：角色 RTM 单文件里只有"调用顺序"，没有"业务规则"。** 允许写"上麦要先抢锁、再读快照、再写回、再释放锁"；不允许写"只有房主能同意上麦"或"joining 状态才能转 active"。后者全部走注入的纯函数。

**规则三：共享 RTC 辅助模块是唯一允许被跨目录 import 的运行时模块，且这是刻意的例外。** 必须在该模块顶部注释与 README 写明理由：角色 RTM 单文件是教材（客户要拷走），RTC 辅助是脚手架（只为让 demo 能听见声音，客户项目里已有自己的 RTC 接法）。**不写明理由，后来者一定会尝试把 RTM 的公共部分也抽成共享基类，那会直接摧毁规则一。**

### 刻意接受的重复

房主端与听众端各自内联同一套 RTM 机制：连接与分阶段回滚、订阅、消息封装与解析、消息去重、Lock 加乐观并发、trace 采集、重连后重新拉取。预计每份约 250 行重复。

**接受它，不抽共享层。** 客户拷一个文件就能跑，比拷两个互相引用的文件有价值。代价是维护时连接与订阅那段要改两处 —— 用"文件骨架模板 + 编写规程"控制，不用抽象控制。

这条同时决定了**文件数按角色数增长，不按人数增长**：多个听众实例都用同一份听众文件，各自传自己的 uid、各自持有自己的 trace。会议室是主持人加参会者两份，互动课堂是老师加学生加助教三份，不会失控。

### 环境配置契约

**只有 appId 一个字段。** 不加区域（两站各部署一份，区域由"部署了哪一份"决定）、不加日志级别、不加场景白名单（可见性是注册表状态字段的职责）。字段集要扩展等到有真实需求，不预留。

优先级链是三层：全局注入变量（线上，最高优先级）→ 构建期环境变量（本地兜底）→ 都缺失则渲染引导页（不是报错页）。

**全局注入必须能覆盖构建期环境变量。** 后者是构建期烧进 bundle 的常量，若让它优先，上层网站永远换不掉 appId。

**源码里没有第三层硬编码兜底。** 体验用 appId 只进本地环境变量文件与本地开发入口页的内联脚本。若写成源码常量，删掉配置后 demo 仍能跑，注入契约就失去约束力。

**要求同步注入，启动时读一次快照。** 上层页面必须在加载 bundle 之前写好全局变量。配置模块在加载时解析一次存进常量，**不监听后续变化、不轮询、不代理劫持全局对象**。支持异步注入意味着要引入"等待配置"的加载态、以及注入迟到时已建立的 RTM 连接如何重连 —— 收益不成比例。这条要求写进 README 的注入契约一节。

### 身份推导

**不做"填表进房"。** 点二级 tab 直接进场景并自动连接，零表单。appId 来自环境配置，token 默认不需要，房间号与 uid 自动生成 —— 表单已无输入项可填。

房间号形如"场景名加 6 位 base36 随机段"，uid 形如"角色前缀加 6 位随机段"。**角色前缀必须保留** —— 时间线的 uid 标记依赖它做可读区分。

URL query 可覆盖房间号与本端 uid，用于两人对连同一个房间做真实联调。覆盖值**不写入任何 storage**，只从 URL 读。刷新时 URL 还在，行为稳定；分享链接即可让对方进同一个房间。新骨架的运行时配置一律不落 storage，每次刷新重新推导。

覆盖参数为 `?room=` 与 `?uid.<role>=`。一个标签页同时跑多端，"本端"没有唯一指代，所以 uid 覆盖按角色键化；`?uid=` 保留为**主角色**（角色列表第一项）的简写。覆盖值缺少角色前缀时自动补齐（`?uid.host=alice` 得到 `host-alice`），已带前缀的不重复补；剥掉前缀后主体为空的覆盖值（如 `?uid.host=host-`）视为无效并回落到自动生成 —— 裸前缀满足前缀不变式却没有区分度，两端各写一次就会撞成同一个 uid，而我们刻意不做冲突检测。（此项由票 `14` 在实现时扩展，spec 同步记录。）

同一标签页内两端的 uid 必须不同，由角色前缀加各自独立随机段保证，**不做冲突检测**。

身份推导归实验室外壳的职责。角色 RTM 单文件只接受构造参数传入的 uid，保持零依赖。

### 路由

路由形如"一级分类 / 二级场景"。渲染前先过配置判定：未配置则渲染引导页，不进场景。

场景 id 用 kebab-case、**不带一级分类前缀**（`voice-room` 而非 `social-voice-room`）—— id 出现在 URL 里应当稳定，前缀会在场景归类调整时造成 id 变更。

### 场景注册表

8 个一级分类：社交、教育、企业、物联网、内容、医疗、出行、游戏。

二级条目**只有 4 个字段**：id、标题、一句话摘要、状态。从遗留场景目录明确丢弃的字段及理由：

| 丢弃字段 | 理由 |
| --- | --- |
| 画布类型 | 服务于"一套通用 UI 数据驱动渲染 24 个场景"，与"一场景一份 RTM 单文件 + 独立主容器"正面冲突 |
| 初始状态 / 动作 / 后继状态 / 事件文案 / 语气 | 假状态机，是模拟层的输入。留着会诱导后来者继续写模拟 |
| 是否支持真实 RTM | 新架构下已实现的场景都是真的，未实现的用状态字段表达 |
| 角色清单 / 能力标签 | **不进注册表但不丢弃** —— 归档为实现资料，由后续每个场景的 effort 取用 |

状态字段**只有"已实现"和"已规划"两个值**。不引入"进行中" —— 它是过程状态，会诱使人把半成品合进主干；一个场景要么可点进去玩，要么标明未建。

本阶段唯一"已实现"的是语聊房（归社交），由遗留的两个语聊房场景合并而来。其余 22 个"已规划"。

**已规划场景的表达：tab 可见、可点、进去是统一占位页**，写明该场景计划演示哪些 RTM 能力并指向语聊房。不灰置（客户会以为坏了）、不隐藏（违背"让客户看见 RTM 能覆盖多少场景"的展示目的）。23 个 tab 本身就是在说"RTM 能做这些"，占位页把"未实现"变成"路线图"。

### 角色 RTM 单文件的契约

**导出场景语义方法，不是 RTM API 的扁平薄包装。** 房主端导出：连接、断开、同意上麦申请、拒绝申请、邀请上麦、强制静音麦位、强制下麦、踢出成员、封禁成员、更新公告、发公屏消息、发表情、发礼物。听众端导出：连接、断开、申请上麦、取消申请、接受邀请、拒绝邀请、设置自己静音、主动下麦、发公屏消息、发表情、发礼物。两端都暴露一个可订阅的 trace store。

每个方法内部写明"这个业务动作要按什么顺序调哪些 RTM API"。客户打开文件即看到"上麦要调哪些 RTM API"，也能把方法直接调进自己项目 —— 这是"可拷走集成"卖点的核心。

遗留的单端编排器用一个 15 条命令的联合类型加 `execute(command)` 分发，现按角色拆到上面两个类。**静音与下麦各自分化成两个语义不同的方法**：房主侧是强制静音与强制下麦（对他人、需要对端确认），听众侧是设置自己静音与主动下麦（对自己、不需确认）。原先靠"目标 uid 是否为空"来区分的隐式分支被消掉，这是拆分带来的净收益。

### 注入一个 reducer，不注入十几个转移函数

规则二要求业务规则外置，但逐个注入 14 个转移函数会让构造参数失控。改为注入**一个状态适配器对象**，它有三个成员：生成初始快照、把从 RTM Storage 读回的数据校验归一（**无效返回空值，由调用方兜底**，不要沿用"无效返回兜底值"）、以及一个纯函数 reducer（禁止 I/O）。

三个函数全部住在场景目录且全部是纯函数。角色 RTM 单文件只知道"调 reducer 得到下一个快照"，不知道任何权限或状态机规则。

构造参数还包括：appId、房间号、本端 uid、显示名、可选 token（默认空，保留参数位）、出站事件处理器、可选的命令确认超时。

代价是语义方法内部多一层动作构造。收益是构造参数从 15 个函数降到 1 个对象，且复制到新场景时注入点只有一处要改。**这是有意的取舍，不要在实现时"简化"成直接 import 转移函数模块** —— 那会违反规则一。

### 出站事件

四个回调：链路状态变化、房间快照更新、互动事件（公屏消息、表情、礼物）、错误。

只用链路状态事件，**不用已废弃的旧状态事件**。token 事件只把"即将过期"当作即将过期。

### 内联的 RTM 机制（两份文件各一套）

以下全部从现有分层代码下沉进角色 RTM 单文件内部，是客户真正要拷走的部分。

**消息封装、TTL 与去重。** 每条 RTM 负载包进一个信封：协议版本号、消息 id、房间与目标校验字段、过期时间戳，默认 TTL 15 秒。接收路径固定为：解析信封 → 去重判定 → 分发。去重上限 500 条。

**治理命令的确认机制。** 踢出、封禁、强制静音、强制下麦这四类命令标记为需要确认，登记超时定时器，等待对端回确认消息。超时未收到则触发错误回调。

**RTM Storage 是房间权威状态，配合 Lock 做乐观并发。** 变更流程固定：获取房间级 Lock → 重新读快照 → 过 reducer → 带版本号写入 → 在 finally 中释放锁。channel metadata 使用单个固定 key。**禁止在这个变更流程之外改快照。**

**Lock 必须先创建才能获取。** 保留现有实现踩出来的处理：遇到"锁不存在"错误码则创建后重新获取，并容忍对端客户端抢先创建导致的"锁已存在"竞态。改动锁相关代码时必须保留这套处理。

**连接分阶段回滚。** 用布尔标记记录 RTM 已连接、已订阅等进度，出错时逆序清理，**并吞掉清理过程中的异常**让最初的失败原因暴露出来。新增步骤沿用同一模式，不要加无保护的 await。

**在登录之前注册事件。** Message、Presence、Storage、Lock 一起订阅。Presence 查询沿分页游标取全部在线用户。

**重连靠重新读取，不靠重放。** 链路状态从"重连中"回到"已连接"时，重新订阅、重新拉 Presence 与 Storage，按最终快照对账麦克风状态。

### 麦位激活由媒体结果驱动

这条顺序**不能改**，UI 与端到端测试都依赖它：房主同意申请或听众接受邀请后，麦位先进入"正在加入"并写入 Storage；然后听众端发布麦克风；成功则麦位转"已上麦"并写入 Storage，失败则回滚麦位并写入 Storage。

这是唯一一处 RTC 结果反向驱动 RTM 写入的地方，也是 RTC 层不采集 trace 却仍能在时间线上看懂因果的原因 —— RTC 的成败会体现为后续那次 RTM 调用的出现或缺席。

### trace 数据模型

每条 trace 条目的字段：实例内单调递增序号（归并时作同毫秒的稳定次序）、时间戳（归并主排序键）、类型、角色、uid、名称（API 方法名或事件名）、可选的短摘要（不放完整对象）、可选耗时（仅 API）、可选错误码与错误信息（仅 API）。

类型**只有两个值**：调 RTM API 出一个 api 节点，收到 RTM 事件出一个 event 节点。

**uid 与角色由实例自己贴**，不由业务层读取时补 —— 归并后来源不能丢。

导出为**可订阅对象**而非裸数组：时间线是本 demo 的核心展示物，"API 被调用的瞬间节点就出现"值得那约 25 行订阅样板；视图层配标准的外部 store 订阅钩子，无需轮询与整数组 diff。读取接口返回只读快照，业务层不得改写。

**单实例环形上限 500 条**，超出**静默丢弃最旧**。作为模块常量，客户拷走后可自行调整。

### 归并与筛选

归并模块订阅两份 trace store，按时间戳归并，同毫秒用实例内序号作稳定次序。

面板支持三维筛选：uid、角色、类型。三者都是条目上已有字段，**不需要为筛选新增数据字段**。筛选是纯 UI 层过滤，不影响 trace 采集、不影响环形缓冲的丢弃逻辑 —— 被筛掉的条目仍在 store 里，取消筛选即恢复。筛选状态是面板自己的局部状态。

**不做"已截断"提示。** 超限静默丢弃。保留清空与折叠。

时间线**只呈现 RTM**，RTC 层不采集 trace —— 混入 RTC 节点会稀释"RTM 数据流"这条主线。若实测发现看不懂中间发生了什么，再考虑加一类媒体节点（记入未决，不在本文定）。

### 共享 RTC 辅助模块

全场景共享单份，只做四件事：加入频道、开关麦、开关摄像头、订阅远端。对外提供注册事件、加入、离开、发布与取消发布麦克风、设置麦克风静音、发布与取消发布摄像头、设置摄像头静音、取本地视频轨道这些能力；事件回调覆盖连接状态、远端音频发布状态、远端视频轨道、音量。

token 字段**从签名去掉**（默认无 token 鉴权），现有的可选 token 参数是要删的历史包袱。**屏幕共享不做** —— 会把 RTC 从辅助扩成一等能力。

**只有实际开音视频的用户创建 RTC 实例。** 多用户场景只允许一人开麦开摄像头，所以同一时刻页面内通常只有 1 个 RTC 客户端。

**音频内部直接播，视频交出轨道。** 这个不一致是刻意的，要在模块顶部注释写明理由，避免后人"统一"掉：音频没有渲染位置，交出轨道只会让业务层多做无意义的事；视频在视图框架下容器挂载时机与播放时机有竞态，交出轨道让组件在自己的副作用里对自己的 ref 播放才做得干净，这也是官方示例的写法。

远端视频轨道生命周期跨模块边界，约定：**远端取消发布或本端离开时，先以空轨道通知 UI 停播，再做取消订阅。** 顺序反了会导致 UI 播放已销毁的轨道。

**"只有一人开音视频"的约束落在模块层，不只靠 UI。** 模块内部维护单实例语义：已有实例时再次加入先离开（现有实现已是这个行为，保留）。UI 层同步灰置非持有者的开关并给出原因文案，而不是静默禁用。客户拷走这个模块后 UI 是他自己的，所以约束不能只在 UI。

现有 RTC 层两处裸抛的用法错误统一走归一后的错误类型，便于业务层区分"用法错误"与"SDK 错误"。

**摄像头相关能力是新增，不是迁移** —— 现有 RTC 层是纯音频的，收到远端发布时对非音频轨道直接丢弃。

### 整页布局骨架

自上而下四层：一级 tab 条（左侧 logo，中间 8 个分类，右侧配置提示）、二级 tab 条（药丸形，当前一级分类下的场景）、主体（演示主区加时间线面板）、以及预留但本阶段不实现的页面底部可折叠区（场景说明与能力标签）。

- 主区与时间线比例 **1fr 比 400px**，时间线固定宽。
- 时间线可折叠成 **40px 竖条**（竖排标题加条目计数），折叠态主体变 1fr 比 40px。
- **1240px 及以下断点**：退化为单列，时间线从右侧栏变为主区下方的横排区块。
- 切换场景只替换主区内容，两级 tab 与时间线面板位置不动。
- 两级 tab 用**原生横向滚动加隐藏滚动条**。**不加**参考 UI 上的左右箭头，**不加**键盘导航 —— 参考 UI 在这一点上不照抄。

### 语聊房主区布局

主区放两台手机外框（房主视角、听众视角），每台上方一个身份条：彩色 uid 标记加角色文案。这是"一个标签页两个真实客户端"的可视化。

手机内部高度约束（已经用户两轮修改确认，**不要回退**）：手机高度取 812px 与视口高度减 210px 的较小值；内部**只有公屏区域滚动**，其余区块钉住不收缩；**底部输入条常驻手机框内**，不随公屏滚动；麦位方框最小高度 76px、头像 26px、4 列网格。

手机内区块顺序：状态栏、房间头部（标题与主题加模式、在线数、版本号三个 chip）、麦位网格、角色专属面板（房主看审批列表，听众看自己的申请状态）、成员条（横向滚动，超出显示计数）、公屏、底部操作条（两端按钮不同）。

### 时间线条目形态

单列、按时间归并**交错**呈现，**不按端并列分栏** —— 本 demo 要展示的是"一个动作在两端引发的因果链"，分栏会把因果拆散。

行布局是三列网格：色点轨道 16px、时间 62px、正文自适应。时间格式砍掉小时只显示分秒毫秒。正文首行是 uid 标记加方法名或事件名，次行是摘要。api 与 event **靠左侧色点区分**，面板顶部给图例。uid 标记颜色按角色固定，与手机身份条上的标记同色。

### 双客户端的生命周期守卫

语聊房主容器用同一个客户端工厂创建房主端与听众端，**先连房主再连听众**，用一个生命周期计数器守卫每个异步步骤，避免视图框架严格模式下的重复挂载与卸载泄漏连接。测试注入假工厂。

**两端都会真实播放音频，人工验证时必须戴耳机。** 保留现有的耳机告警。

### 必须保留的生产边界告警

踢出、封禁、强制麦控都是**客户端协作行为，不构成信任边界**。页面必须显式渲染这条告警，保持现有表述，**不要改写成"已强制执行的权限控制"**。

### 依赖可安装化

当前状态：RTM SDK 依赖指向某台机器上的本地绝对路径，换机器安装直接失败。这是开源的硬阻塞。

处理方式：把未发布的 SDK 包（已核验为 2.3.0 正式版、零 runtime 依赖、Apache license）复制进仓库根的 vendor 目录，依赖改为**相对路径**引用，清掉锁文件里的绝对路径条目后重装。RTC SDK 从浮动版本**锁到确定版本**，其余写浮动版本的依赖一并锁定 —— 开源项目不应让安装结果随时间漂移。待 SDK 发布到 npm 后改为版本号引用并删除 vendor 目录。

vendor 放仓库根。新架构下 23 个场景共处一个应用，"整目录拷走"的产品要求消失 —— 可拷走的单位从"一个 demo 目录"缩小为"一份角色 RTM 单文件"，单文件拷走不需要 vendor 跟随（客户自己从 npm 装 SDK）。

## Testing Decisions

**什么是好测试：只测外部可观察行为，不测实现细节。** 本项目的具体判据是断言"对 SDK 发出了哪些调用、按什么顺序"，而不是断言内部字段或私有方法被调用过。

**沿用现有的调用轨迹范式。** 现有测试的基石是假端口记录一个字符串数组的调用轨迹，再断言字符串序列（形如"rtm 冒号 publish 冒号 user 冒号目标 uid 冒号消息类型"）。**这个范式必须保住** —— 它让房间逻辑完全脱离网络可测，也让测试读起来就是一份调用顺序文档。这是本项目最重要的测试先例。

**注入点从端口下移到 SDK 工厂。** 因为端口接口本身要废弃，角色 RTM 单文件的构造参数增加一个可选的 RTM 客户端工厂，默认值是真实的 SDK 实例化函数，测试传入一个记录调用轨迹的假实现。这是唯一为可测性开的口子，**不算违反零依赖**（默认值就是 SDK，客户拷走后不需要关心这个参数）。RTC 侧同样用假客户端。

**要测的模块与重点：**

- 转移函数模块：纯函数，直接调用，覆盖率要求最高。现有测试可整份迁移复用，迁移后先让它红再让它绿 —— 这是证明行为契约未变的手段。
- 状态适配器：校验无效输入返回空值、reducer 不改入参。
- 两份角色 RTM 单文件：连接顺序与分阶段回滚（含"清理时再抛异常仍暴露最初失败原因"）、锁与乐观并发的完整轨迹（含两个锁相关错误码的处理路径）、信封校验与去重、治理命令的确认与超时、每个语义方法的调用轨迹、trace 采集、重连重新拉取。
- trace store：环形上限的丢弃行为、只读快照、订阅通知。
- 归并模块：同毫秒的稳定次序、归并后来源字段不丢。

- 场景注册表：分类与场景清单、**断言条目没有多余字段**（这是防止已丢弃字段被顺手加回来的护栏）、状态取值范围。

- 语聊房主容器：双端编排顺序、严格模式下重复挂载不泄漏连接、麦位由媒体结果驱动的三条路径（进入正在加入、成功转已上麦、失败回滚且有可见反馈）、耳机告警与生产边界告警存在且**告警文案不含"已强制执行"这类表述**。

## Further Notes

### 必须在建造前或建造中解决的

1. **仓库一个 commit 都没有。** 开源前需要建立基线 —— 但 git 提交类操作必须由用户显式发起，**不要擅自 commit**。
2. **两站域名白名单未核实。** 国内站与国际站是不同域，这是从"两站分立"推出的必然结果，**不是查证过的事实**。写进 README 前必须核对官方防火墙白名单页面。
3. **appId 大概率要分两套** —— 两站是不同的声网项目、接入不同区域网关。注入契约本身不受影响（单字段，两站各注入自己的值），但部署时要确认。

### 建造中会浮现的张力（已知，不是缺陷）

4. **两份角色 RTM 单文件约 250 行重复**是刻意的。若实现时发现重复远超预期（比如超过文件的 60%），回头讨论"是否用代码生成而非抽象"来解决，**但不要抽共享基类**。
5. **摄像头能力是新增**，现有 RTC 层纯音频。语聊房本身不需要摄像头，这部分能力在语聊房里没有验证场景 —— 可以等第一个视频场景再实现，本阶段只把接口留出来。

### README 必须声明三件事

缺一不可，交付清单要检查：

1. **多 RTM 客户端实例是实测可行、官方文档未保证。** 官方迁移指南写明事件回调绑定到客户端实例，跨实例行为无任何说明。一角色一个实例是本项目的地基，不写明这一状态，客户照抄进生产、日后 SDK 行为变化时会误判归因。来源：<https://docs.agora.io/en/realtime-media/rtm/reference/migration-guide/web>
2. **治理动作不构成信任边界**，生产环境必须在服务端校验。
3. **默认 appId 无 token 鉴权，仅供体验**，接入生产必须换成支持 token 的 appId 并在登录时传入 token。

另需一节说明**"为什么 RTM 一角色一份而 RTC 共享一份"**（规则三的理由）。**这节不能省** —— 少了它，后来者一定会尝试抽 RTM 共享基类。
