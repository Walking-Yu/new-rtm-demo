# 语聊房迁移到新骨架的切分

Type: grilling
Status: resolved
Blocked by: 01, 02, 05, 06, 07

## Question

现有 `demos/voice-room/`（约 2700 行）如何切分并迁移到新骨架，成为样板场景？

需要定：

- 现有各层的去向：`domain/transitions.ts`（17 个纯函数状态机）、`domain/protocol.ts`（envelope + 去重）、`RoomStateRepository`（Lock + majorRevision）、`VoiceRoomClient`（686 行编排器）、`components/`、`app/`。
- 哪些代码进语聊房的 `rtm.ts`，哪些留在场景目录的业务状态机文件，哪些进共享骨架。
- 业务状态机注入 `rtm.ts` 的具体签名。
- 现有 `MemoryRtmPort` / `MemoryRtcPort` 的 operations 轨迹测试范式如何在新形态下保留——这是现有测试的基石，不能在迁移中丢掉。
- 现有 E2E 测试的处置。
- 迁移是原地改造还是新建目录后逐步搬迁；旧 `demos/voice-room/` 何时删除。

被阻塞原因：需要先知道场景目录结构（`01`）、`rtm.ts` 契约（`02`）、trace 形状（`05`）、env 链路（`06`）、rtc 边界（`07`）。

## Answer

### 一、文件按角色切分（用户决策）

**一个主持人一份 `rtm.ts`，多个参与者共享一份 `rtm.ts`。** 理由是参与者之间除了 uid 不同，调用的 API 完全一样，没有理由为每个参与者各写一份。

语聊房因此是两份文件：

```
scenes/voice-room/
  rtm-host.ts        房主：审批上麦、禁麦、强制下麦、踢人、封禁
  rtm-audience.ts    听众（多实例共享此文件）：申请上麦、接受邀请、主动下麦
```

命名用**角色**，不用 uid —— uid 是运行时值，由构造参数传入，不进文件名。多个听众实例都 import 同一个 `rtm-audience.ts`，各自 `new` 一个实例、各自传自己的 uid、各自持有自己的 trace。

这条同时消化了 `05` 遗留的膨胀张力：文件数按**角色数**而非**人数**增长。会议室是主持人 + 参会者两份，互动课堂是老师 + 学生 + 助教三份，不会失控。

### 二、两份文件之间的重复：接受它

`rtm-host.ts` 与 `rtm-audience.ts` 都要 login、subscribe、读写同一个 Storage key、抢同一把锁，这部分代码重复。**接受这个重复**，不抽共享层 —— 抽了就破坏 `02`/`05` 定下的零依赖，客户拷一个文件就跑不起来。

Demo 项目里的重复是特性：客户只关心自己那一侧的角色，拿到一份完整可跑的文件比拿到两个互相引用的文件更有价值。代价是维护时连接/订阅那段要改两处，通过「文件骨架模板 + 编写规程」控制，不通过抽象控制。

### 三、现有 `domain/` 的归属

现有 `demos/voice-room/src/domain/` 有四块，去向不同：

| 现有内容 | 去向 | 理由 |
| --- | --- | --- |
| `VoiceRoomSnapshot` 类型 | **留在场景目录** `state.ts` | 业务状态形状，两份 `rtm-*.ts` 都 import 它作类型（类型 import 不破坏零依赖，编译后消失） |
| 17 个纯函数转移 | **留在场景目录** `transitions.ts` | 按 `02`：`rtm.ts` 不含「谁有权限、什么状态可转移」的规则，这些以回调注入 |
| `protocol.ts` envelope + 去重 | **进 `rtm-*.ts` 内部** | 这是 RTM 消息层机制（schemaVersion、messageId、TTL、去重），属于「怎么用 RTM 发消息」，正是客户要拷走的部分 |
| `RoomStateRepository` 的 `mutate` | **进 `rtm-*.ts` 内部** | Lock + majorRevision 乐观并发是 RTM Storage 用法精华，必须在可拷走的文件里 |

即：**RTM 机制下沉进 `rtm-*.ts`，业务规则留在场景目录**。这与 `02` 的边界定义一致。

### 四、目录形态

```
src/
  app/                    路由、两级 tab 导航、env 读取
  scenes/
    registry.ts           场景注册表（01 定的结构）
    voice-room/
      index.tsx           main container（该场景的页面）
      rtm-host.ts         ← 可拷走
      rtm-audience.ts     ← 可拷走
      state.ts            快照类型
      transitions.ts      纯函数转移（注入给 rtm-*.ts）
      config.ts           客户端数量上限等场景配置（08）
  shared/
    rtc.ts                共享 RTC 辅助（07）
    timeline/             时间线面板组件 + 归并逻辑（05）
    ui/                   通用外壳组件
vendor/
  agora-rtm-2.3.0/        未发布的 SDK 包（03/11）
```

`vendor/` 放在仓库根。这解掉了 `03` 留下的位置张力：新架构下 23 个场景共处**一个**应用，不再有「voice-room 整目录拷出去」的产品要求 —— 可拷走的单位从「一个 demo 目录」缩小为「一份 `rtm-<role>.ts`」，而单文件拷走不需要 vendor 目录跟随（客户自己从 npm 装 SDK）。

### 五、遗留代码处置

`demos/voice-room/` 与根 `src/`（遗留 24 场景实验室）都不再是主线。本阶段**不删除**，新骨架在 `src/` 下重建，遗留实验室从路由摘除即可；真正的删除时机留给 `11`。
