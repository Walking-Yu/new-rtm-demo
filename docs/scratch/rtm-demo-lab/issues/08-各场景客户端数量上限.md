# 各场景客户端数量上限

Type: grilling
Status: resolved
Blocked by: 04, 07

## Question

每个二级场景在一个页面里跑几个真实客户端？超出部分怎么表现？

需要定：

- 统一的默认上限，以及需要更多端的场景（会议室、互动课堂、直播多嘉宾）如何处理。
- "只允许一个人开语音和摄像头，其他默认关闭"这条约定如何在代码里落地：是 UI 层禁用，还是 `rtc.ts` 层面只允许一个实例持有采集设备。
- 模拟端与真实端如何在 UI 上区分，避免客户误以为模拟端也是真实链路。
- 每个场景的人数上限记录在哪（场景注册表的字段，还是场景目录内的配置）。

已定前提：涉及多用户的场景只允许一个人开语音和摄像头，其余默认关闭；具体人数上限按二级场景逐个约定，实现时提供。

被阻塞原因：`04` 决定单页面多 RTM/RTC 实例的技术上限，`07` 决定 RTC 采集设备的持有方式。

## Answer

### 没有技术上限，只有体验上限

`04` 已定：RTM 一页可跑多个 client（不同 uid），`07` 已定：只有实际开音视频的那个用户创建 RTC 实例。因此**不存在"超出上限要退化成模拟端"的问题** —— 原票里"1 个真实端 + 其余模拟"的备选方案作废，所有端都是真实链路。

上限由**体验**决定，不由 SDK 决定：每多一个端就多一份 RTM 连接、多一列时间线、多一块 UI，屏幕和认知都会先撑不住。

### 默认上限 2，按场景在场景目录内声明

- **默认 2 个端**，语聊房即 `host` + `audience`。
- 需要更多端的场景（会议室、互动课堂、直播多嘉宾）**在实现该场景时逐个约定**，不预先为未实现的场景定数字 —— 这些场景本阶段全部是占位（见 `01`）。
- 上限**不进场景注册表**。注册表按 `01` 只保留 `id`/`title`/`summary`/`status` 四个字段，端数是场景内部实现细节，写在场景目录自己的配置里（与 `rtm-<role>.ts` 同级），随场景代码一起被拷走。

### "只有一人开音视频"落在 `rtc.ts` 层，不只靠 UI

UI 层禁用是必要的（灰置其他端的开麦按钮），但不足以作为保证 —— 客户拷走 `rtc.ts` 后 UI 是他自己的。因此约束落在模块层：

- `rtc.ts` 内部维护**单实例语义**：同一时刻只允许一个 RTC client 持有采集设备。已有实例时再次 `join` 先 `leave`（现有 `AgoraRtcAdapter.join` 已是这个行为，保留）。
- 业务层负责决定"当前哪个角色持有麦克风/摄像头"，切换时先释放再获取。
- UI 层同步灰置非持有者的开关，并给出原因文案（"当前由房主占用麦克风"），而不是静默禁用。

### 模拟端与真实端的区分：不适用

本阶段没有模拟端，所以这一子问题在当前范围内无需解决。若后续某个场景确实需要模拟端（例如要展示 100 人房间的 Presence 列表），届时再定标注方式 —— 已记入地图 Not yet specified。

### 与"一角色一份 `rtm-<role>.ts`"的连带后果

端数上限直接等于该场景 `rtm-<role>.ts` 的文件数。这是文件数膨胀的根源，也是把默认值压在 2 的另一个理由：角色越多，重复的 RTM 调用序列越多。这条张力的正面处理仍在 `10`。
