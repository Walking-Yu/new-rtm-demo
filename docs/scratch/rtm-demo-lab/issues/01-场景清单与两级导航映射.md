# 场景清单与两级导航映射

Type: grilling
Status: resolved
Blocked by: —

## Question

遗留 `src/domain/scenarioCatalog.ts` 有 8 个一级分组、24 个场景；`docs/inputs/index.md` 要求 8 个一级分类、23 个二级场景。一级分类完全一致，二级切分粒度不同（例如遗留把语聊房拆成 `voice-room-interaction` 和 `voice-room-seats` 两个场景，输入文档要求合成"语聊房"一个）。

需要定下：

1. 23 个二级场景的最终清单与 id 命名规则。
2. 每个二级场景与遗留 catalog 条目的映射关系：复用、合并、拆分、还是全新。
3. 从遗留 catalog 保留哪些元数据字段。已知 `roles`、`capabilities` 值得留；`canvas` 要丢（它服务于"通用 UI 数据驱动渲染"，与"一场景一份 rtm.ts + 独立 main container"互斥）；`initialStatus` / `actions` / `nextStatus` / `eventText` 是模拟层用的，去留待定。
4. 新的场景注册表放在哪、什么形态，以及"建设中"状态如何表达（23 个场景中只有语聊房会在本阶段实现）。

## 已知前提

- 遗留 24 个场景里只有 `voice-room-seats` 和 `device-control` 两个 `supportsRealRtm: true`，其余 22 个是纯 UI 模拟。除语聊房外的场景都是首次真实实现，不是迁移。
- 遗留 catalog 作为"种子"使用：留元数据，弃执行层（canvas / simulation / realScenarioRuntime）。

## Answer

**范围缩小（用户决定）：除语聊房外，其余场景一律先空着。** 本票因此不再定 23 个场景的逐项切分，只定三件事：注册表结构、语聊房这一条真实条目、其余场景的占位表达。

### 1. 注册表只登记「导航需要的东西」

一级分类沿用输入文档与遗留 catalog 已对齐的 8 个（`social` / `education` / `enterprise` / `iot` / `content` / `healthcare` / `mobility` / `gaming`），保留遗留的 `label` 与 `shortLabel` —— 参考 UI 的一级 tab 带左右滚动箭头，窄屏需要短标签。

二级条目只保留 4 个字段：`id`、`title`、`summary`、`status`。

**从遗留 catalog 丢弃的字段及理由：**

- `canvas` —— 服务于「一套通用 UI 数据驱动渲染 24 个场景」，与「一场景一份 rtm.ts + 独立 main container」正面冲突（既定决策 8/10）。
- `initialStatus` / `actions`（含 `nextStatus` / `eventText` / `tone`）—— 这是 `simulation.ts` 的输入，是假状态机。新架构下状态来自真实 RTM，动作来自场景自己的语义方法。留着会诱导后来者继续写模拟。
- `supportsRealRtm` —— 新架构下每个已实现场景都是真的，这个字段失去意义；未实现的用 `status` 表达。
- `roles` / `capabilities` —— **不进注册表，但不丢弃**。它们是有价值的设计输入（`capabilities` 标注了每个场景该演示哪些 RTM 能力），但属于「实现某个场景时要读的资料」，不是「渲染导航要读的数据」。归档到 `docs/` 下的场景资料文件，由后续每个场景的 effort 各自取用。

### 2. `status` 只有两个值

`'ready' | 'planned'`。本阶段只有语聊房是 `ready`，其余 22 个 `planned`。

不引入 `'in-progress'`：它是过程状态，会诱使有人把半成品合进主干；一个场景要么可点进去玩，要么标明未建。

### 3. 「建设中」的表达：tab 可见、可点、进去是说明页

三种候选里选这个：

- ~~灰置不可点~~ —— 客户会以为坏了。
- ~~折叠隐藏~~ —— 违背「让客户看见 RTM 能覆盖多少业务场景」这一开源展示目的。
- **可点，进去是一个统一的占位页**，写明该场景计划演示哪些 RTM 能力（取自归档的 `capabilities`）、以及去哪看已实现的语聊房。

理由：这个实验室对客户的第一价值是「场景地图」—— 23 个 tab 本身就是在说「RTM 能做这些」。占位页把「未实现」变成「路线图」，比灰置更诚实也更有用。

### 4. 语聊房的合并

遗留 `voice-room-interaction`（弹幕/礼物/表情）与 `voice-room-seats`（上下麦/麦位锁）合为一个二级场景 `voice-room`，归入 `social`。这是唯一一条 `ready`。

`social` 下遗留还有 `social-presence`、`social-chat`、`live-social-pk`、`one-to-one-call`、`room-moderation`，与输入文档的【社交关系，社交聊天，直播，1v1 视频，房间治理】对应，全部登记为 `planned`。

### 5. id 命名规则

kebab-case，业务语义优先，**不带一级分类前缀**（`voice-room` 而非 `social-voice-room`）。前缀会在场景归类调整时造成 id 变更 —— 而 id 会出现在 URL 里，应当稳定。一级分类作为独立字段表达归属，不编码进 id。

### 6. 注册表位置

留给 `10`（语聊房迁移切分）连同新骨架目录形态一起定。本票只定内容与结构，不定路径 —— 目录形态还没决定，先定路径会是空猜。

### 推迟到各场景自己的 effort（已从本图迷雾中移除）

- 「司机」与「骑手」是否应为两个独立二级场景（看着像角色而非场景，遗留用一个 `driver-rider-messaging` 涵盖两者）。
- `social` 的「直播」与 `content` 的「直播间」语义重叠（遗留对应 `live-social-pk` 与 `live-chat-gifts` 两个不同侧面）。

两者都只在真要实现那个场景时才需要答案，现在消耗判断力没有收益。
