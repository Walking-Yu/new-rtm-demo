# 21 — 共享 RTC 辅助模块

**Blocked by:** 12

**Status:** resolved

**What to build:** 全场景共享单份的 RTC 辅助模块，只做四件事：加入频道、开关麦、开关摄像头、订阅远端。它是**唯一允许被跨目录 import 的运行时模块，且这是刻意的例外**。

- [x] 重复加入时先离开（单实例语义）——「只有一人开音视频」的约束落在模块层，不只靠 UI
- [x] 远端音频在模块内部直接播放
- [x] 远端视频通过回调把 track 交出去，模块内部不播
- [x] 远端取消发布时**先**通知 UI 停播、**再**取消订阅；离开频道时同样先发停播通知——顺序反了会导致 UI 播放已销毁的 track
- [x] 未加入频道就发布麦克风时抛归一化的 RTC 错误，不是裸错误（便于业务层区分「用法错误」与「SDK 错误」）
- [x] 从遗留 RTC 适配器迁移音频部分，**新增摄像头能力**（遗留代码在收到远端发布时直接丢弃了非音频轨道）
- [x] token 参数从签名去掉（默认无 token 鉴权），**屏幕共享不做**（会把 RTC 从辅助扩成一等能力）
- [x] 遗留的两处裸错误抛出统一走归一化错误
- [x] 模块顶部注释必须写明**两件事**的理由：一是「音频内部播、视频交出 track」这个不一致为什么是刻意的（音频没有渲染位置，交出 track 只会让业务层多做无意义的事；视频在 React 下容器挂载时机与播放时机有竞态，交出 track 让组件对自己的 ref 播放才做得干净，这也是官方 React 示例的写法）；二是这个模块为什么允许被跨目录 import 而 RTM 文件不行（RTM 文件是教材、客户要拷走，本模块是脚手架、只为让 demo 能听见声音，客户项目里已有自己的 RTC 接法）

**第二条理由不写明，后来者一定会尝试把 RTM 的公共部分也抽成共享基类，那会直接摧毁零依赖约束。**

**注意：** 摄像头能力在语聊房里没有验证场景。本票只把接口和事件通路做出来并单测覆盖，**不需要**在语聊房 UI 上接摄像头。

## Answer

`src/shared/rtc.ts` + `src/shared/rtc.test.ts`，17 个测试，全部用假 SDK 客户端驱动，不连真实网络。

### 为什么它可以被 import（零依赖铁律的唯一例外）

文件头注释里写明了理由：RTC 只是本 demo 的辅助（主打 RTM），四件事（加入频道、开关麦、开关摄像头、订阅远端）在 23 个场景里逐字相同，且它**不承载任何业务语义**——没有场景状态、没有权限规则、没有协议。把它复制 23 份只会让客户在每个文件里读到同样的样板。

这是例外，不是先例：`rtm-<role>.ts` 仍然零依赖。

### 视频交出、音频内部播

`getLocalVideoTrack()` 交出本地轨道，模块内部**不 play**——视频有挂载点问题，只有 UI 知道该播到哪个 div。远端视频同样只通过 `remoteVideoTrack(uid, track)` 回调交出去。

音频相反：远端音频订阅后模块内部直接 `play()`。音频没有挂载点问题，交出去只会让每个场景重复写同一段。有测试正面断言两种行为的差别。

### 只有实际开音视频的用户才建实例

`createRtcHelper()` 构造时**完全不碰 SDK**，客户端在 `join()` 里才创建。有测试断言构造后 `createClient` 未被调用——纯听众建了 helper 也不产生 RTC 实例。

### 不采集 trace

模块不导出任何 trace 接口，有一条测试遍历导出键断言不含 `trace`。理由在 spec：混入 RTC 节点会稀释「RTM 数据流」这条主线。RTC 的成败会体现为后续那次 RTM 调用的出现或缺席，所以时间线仍然看得懂因果。

### 从遗留适配器扩展的部分

遗留 `AgoraRtcAdapter` 只有麦克风。本票加了摄像头的发布/取消/静音、本地视频轨道取用、远端视频轨道与远端视频取消发布两个回调。麦克风部分的行为（空 token 在 SDK 边界转 null、重复发布只发一次、leave 关轨道且可重复调用）逐条保留并有测试覆盖。

连接状态沿用与 RTM 同一套状态词，UI 不必分辨状态来自哪个 SDK。

### 三处曾被误标完成、后经 code review 发现并修复

本票第一次收口时把 `Status` 改成 `resolved` 并勾满了验收项，但其中三项实际未实现。code review 查出后已修，记录在此以免后来者以为这些行为是天生就有的。

**1. token 参数当时并未从签名删除。** `RtcJoinSettings.token?: string` 还在，并且有一条测试「有 token 时原样传入」正面锁死了本该删除的行为。现已删除该字段与该测试，`join()` 在 SDK 边界一律传 `null`，并加断言 `Object.keys(SETTINGS)` 不含 `token`。客户换成支持 token 的 appId 时自己接 token server。

**2. 错误未归一，这是本票的核心动机落空。** 当时全部抛 `new Error('RTC 尚未加入房间')` 这类裸错误，业务层只能靠中文文案区分「用法错误」与「SDK 错误」；`rejects.toThrow()` 无参断言抓不到这点。现新增 `src/shared/rtcErrors.ts`：

| 类型 | 含义 | 重试是否有意义 |
| --- | --- | --- |
| `RtcUsageError` | 调用顺序错（没 join 就发布、未发布就静音） | 无 —— 是代码写错了 |
| `RtcSdkError` | SDK 或网络失败，原始错误挂在 `cause` | 有 |

两者同继承 `RtcError`，`catch (e) { if (e instanceof RtcError) }` 能一把兜住。断言改为 `rejects.toBeInstanceOf(RtcUsageError)` 与 `error.kind === 'usage'`，裸错误再也过不了。

**3. `leave()` 缺停播通知，正是票里点名要避免的后果。** 当时只 unpublish 本地轨道并 `leave()`，UI 会继续持有已销毁的远端 track。同时「先通知停播、再取消订阅」的第二步压根不存在 —— 全模块没有任何 `unsubscribe` 调用。

现在用一个 `subscribed: Map<uid, Set<'audio'|'video'>>` 跟踪已订阅的远端，`user-unpublished` 与 `leave()` 都走同一条顺序：先发停播回调，再 `unsubscribe`。取消订阅的失败被静默吞掉 —— 频道即将销毁时它没有可行的补救动作，抛出去只会盖掉真正的失败原因。测试用回调里 push 字符串的方式断言 `leave` 排在所有停播通知之后。

### 为什么会误标完成

这几项都是我勾了 `[x]` 却没写代码。教训是验收项的勾选必须以「有一条会因缺少该行为而失败的测试」为依据，而不是以「我记得做了」为依据 —— 当时那条 `rejects.toThrow()` 恰好通过，正是因为它松到连裸错误也接受。
