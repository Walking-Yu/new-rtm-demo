# rtm.ts 契约与目录形态

Type: grilling
Status: resolved
Blocked by: —

## Question

每个二级场景的 `rtm.ts` 对外暴露什么形态的契约？是通用的 RTM 薄包装（扁平映射 RTM API + 一个 `mutate` 高阶方法），还是场景语义方法（`requestSeat()` / `approveSeat()` / `kickMember()`，每个方法内部是具体的 RTM 调用序列）？

同时确定：文件放在场景目录下的什么位置、业务状态机以什么形式注入、trace 数组如何导出。

已定前提（来自地图 Notes，不在本票重开）：

- `rtm.ts` 只承载 RTM 机制，业务状态机以回调注入。
- `rtm.ts` 内部自带 trace 数组并导出，采集底层 RTM API 粒度。
- 零依赖单文件，客户拷走即可运行。

## Answer

选 **B：场景语义方法**。

`rtm.ts` 导出的是该场景的语义动作，语聊房那份即 `requestSeat()`、`approveSeat()`、`kickMember()` 等，每个方法内部写明这个业务动作要按什么顺序调哪些 RTM API。客户打开文件能直接看到"上麦要调哪些 RTM API"，也能把方法直接调进自己项目——这是本项目"可拷走集成"卖点的核心。

代价与已知张力（后续票需要消化）：

- 23 份 `rtm.ts` 各不相同，复制样板做新场景时要重写方法名与调用序列，与"第二个场景一天产出"的验收点存在张力。缓解手段不能是抽共享层（会破坏零依赖决策），只能靠模板化的文件骨架 + 清晰的编写规程。
- 语义方法内部难免夹带业务判断，与"业务状态机回调注入"的边界需要在实现规程里划清：允许 `rtm.ts` 内含"调用顺序"层面的编排，不允许含"谁有权限、什么状态可以转移"层面的规则——后者仍走注入的纯函数。

未决、留给后续票：文件在场景目录中的具体路径与命名、trace 数组的导出形状（`05`）、业务状态机注入的具体签名（`10`）。
